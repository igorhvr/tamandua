## (a) Canonical contract conclusion — operator-notes.local is UNTRACKED

**Conclusion: the canonical contract is UNTRACKED-IN-CLONE.** `operator-notes.local`
must exist in every WORK CLONE as an untracked, byte-identical inert file; it must
NOT be part of the committed golden tree. This resolves the E2.3/E2.4 split in
favour of the provisioning guard (option 2a of the task), with explicit citations:

- `tamandua-torture-test-spec/02-fixture-projects.md` §"Junk probes, two classes":
  > "*inert operator junk* — one `operator-notes.local` per repo, **planted at
  > instantiation**, never touched by any tool: **must stay untracked** and
  > byte-identical all campaign (hashed by the 1-min sampler...)"
- Same section, load-bearing clause:
  > "This is load-bearing: TSTX committed-tree keying and the tracked-dirty gate
  > must tolerate harmless untracked junk while hard-failing on tracked drift."
- Same section, fixture-integrity invariant:
  > "Fixture-integrity asserts existence + untrackedness before each wave."

Reading the spec's intent rather than any single sentence: the junk is a
working-tree probe of *agent behaviour* — by definition an **untracked** file that
well-behaved agents must neither commit, delete, nor modify. "Planted at
instantiation" (provisioning) is the mechanism that places it in the clone; it is
not a committed file. A golden tree that COMMITS it makes every clone see it as
**tracked**, which violates the literal "must stay untracked" mandate and trips the
provisioning guard's `operator-notes-tracked` fail-closed oracle on every real
provisioning (all 24 Tier-1 real cases TEST_INFRA_FAIL in
campaign-20260811T083804105Z — the honest INFRA_FAILURE observed).

Alternative reading summarised and rejected: a literalist read of "planted at
instantiation" could suggest the golden tree may carry it and provisioning merely
resets it. The spec rejects this: the untracked invariant is stated categorically
("must stay untracked", "asserts existence + untrackedness"), and TSTX keying /
tracked-dirty gating are explicitly designed around UNTRACKED junk tolerance. A
committed (tracked) junk file would silently defeat both of those load-bearing
oracles. So UNTRACKED-in-clone is the only spec-faithful reading.

**No oracle is weakened** by this choice: the fail-closed `operator-notes-tracked`
detector (present ⇢ tracked = infra-fail), the no-commit / no-delete / no-modify
detection (byte-identity vs fixture source + untrackedness + presence) all stay
intact; they are simply aimed at a clone whose golden no longer carries the file.

## E2.4 US-004 (DONE): `$(sentinel)` entity in work clones — SPEC'D HOSTILE-FILENAME PROBE (evidence), not an unexpanded-shell bug

### DECISION
The `$(sentinel)` subdirectory observed in work clones is **SPEC 02's documented

1. **It is a DIRECTORY, not a stray artifact.** Fresh provision
   (`tt-fixture-provision --fixture tt-python --arming raw`) into
   `var/fixtures/work/W-US004-evidence/tt-python` yields
   `stat -c '%F' '$(sentinel)'` → `directory`, containing `canary.py`

   `fixtures-src/tt-python/$(sentinel)/canary.py` → `IDENTICAL`. All canaries
   share blob `418dd3d04e21bcacaa63c8b451603be3b0004af6` in every golden.
3. **It is COMMITTED in the golden tree and TRACKED + clean in the clone.**

   `100644 blob 418dd3d0…  $(sentinel)/canary.py`; in the work clone
   `git ls-files --error-unmatch '$(sentinel)/canary.py'` → tracked, and

5. **Spec 02 documents it.** `tamandua-torture-test-spec/02-fixture-projects.md`
