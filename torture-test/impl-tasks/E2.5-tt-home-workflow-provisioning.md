# E2.5: real cases launch into an unprovisioned TT home — no workflows installed, no daemon preflight

Fifth Tier-1 real launch (campaign-20260812T065206152Z): honest
INFRA_FAILURE, all 24 real cases TEST_INFRA_FAIL with
`workflow-run-identification / missing-run-identifier`. Actual cause
(launch.stderr, W1.L1-python attempt-1):

  Error: No workflow.yml found in
  /home/igorhvr/idm/tamandua/torture-test/var/home/.tamandua/workflows/do-now.
  Expected a workflow specification file.

The real-case launch path correctly targets the CONTAINED TT instance
(torture-test/var/home, ports 43xx per spec 01 two-daemon
architecture) — but nothing in the campaign provisions that instance:
no workflow catalog installed into the TT home, and no preflight
asserting the TT daemon is up and its catalog present before real
cases attempt launches. The controller then misclassifies the launch
failure as a run-identification error (secondary defect: the REAL
error — catalog missing — is buried; the reason category should name
it).

## Work

1. Campaign preflight for real cases (wire into the controller's
   real-case arm and/or the W0.0 assumption gate per spec 04):
   under the CONTAINED TT env (env/tt-env.sh — never the operator's
   ~/.tamandua):
   - provision the TT home if absent (tt-provision-home exists from
     Phase A — use/extend it),
   - install the bundled workflow catalog into the TT home
     (equivalent of `tamandua workflow install --all` against the
     contained instance, using the repo's own dist build),
   - start (or verify) the real TT daemon on the 43xx ports via
     daemon-control, and stop it at campaign end (hygiene: no leaked
     daemons — sweeps must stay clean),
   - fail closed with a DISTINCT reason (`tt-home-unprovisioned`,
     `tt-daemon-down`, `catalog-missing`) if any leg cannot be
     established.
2. Fix the misclassification: a launch stderr containing a definite
   infrastructure error must surface that error as the reason
   category, not `missing-run-identifier` (keep run-identification
   for the genuinely ambiguous case).
3. Idempotence: repeated campaigns reuse the provisioned TT home
   (no reinstall churn when the catalog matches the current build —
   compare a build/catalog stamp), and a stale catalog (older build)
   triggers reinstall, not failure.
4. Prove (zero tokens): with the TT home deleted, a bare
   `./run-torture-test --tier1` still GREEN x2 (local cases must not
   need the real daemon — verify this stays true); then with the
   E2.2-style argv-recording launch stub, an --include-real pass
   shows: TT home provisioned, catalog installed (list the workflows
   present under torture-test/var/home/.tamandua/workflows), daemon
   up on 4339 then stopped at campaign end, first real case reaching
   an actual `workflow run` invocation with a captured run id from
   the stub. Hygiene canary UNCHANGED; no processes/daemons leaked
   after (pgrep + ports 43xx sweeps shown).
