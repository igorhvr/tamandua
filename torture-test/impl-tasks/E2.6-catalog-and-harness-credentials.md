## Implementation closeout (US-004 — minimal-file harness-credential surfacing)

`torture-test/bin/tt-provision-home` no longer copies whole `~/.pi` /
`~/.hermes` directories. It now surfaces an ENUMERATED minimal set, one file
at a time, plus the operator's env-provided API keys materialized into the
contained home:

**pi (`~/.pi/agent/`):**
- `settings.json` — default model/provider/thinking selection; `pi --print`
  (no `--model`) resolves the selected model from here.
- `models.json` — custom provider definitions (`local-dspark`: `baseUrl` +
  inline `apiKey` + model list).
- `auth.json` — produced by the env-key merge: the operator's `auth.json`
  base merged with any SET built-in-provider API-key env vars
  (`DEEPSEEK_API_KEY` → `deepseek`, `OPENAI_API_KEY` → `openai`, etc.), in
  pi's `{"<provider>":{"type":"api_key","key":"..."}}` format (0600).

**hermes (`~/.hermes/`):**
- `config.yaml` — default model/provider + auxiliary slots.
- `auth.json` — OAuth/API-key credential store (openai-codex id_token +
  refresh_token + credential_pool).
- `.env` — operator env API keys written verbatim as dotenv KEY=VALUE lines
  (hermes loads it via `load_hermes_dotenv`).

**Why env keys must be materialized (root cause of the E2.6 `No API key
found` failure):** `daemon-control` starts the contained real daemon with
`env -i` (`env_for_kind`), so the daemon and every pi/hermes it spawns never
inherit the operator's `DEEPSEEK_API_KEY`/`OPENAI_API_KEY`/`ANTHROPIC_API_KEY`
environment. The operator's pi `auth.json` is empty and `models.json` only
defines `local-dspark`, so the `deepseek` built-in provider (the selected
default) had no resolvable API key. Materializing the env keys into files the
harnesses read from the contained HOME (pi `auth.json`, hermes `.env`) makes
the surfaced set self-sufficient.

**Containment preserved:** only the enumerated files are written under the
contained TT home; no `~/.tamandua`, `~/.ssh`, operator gitconfig, `~/.hermes`
`state.db`/`sessions`/caches are surfaced. The hygiene canary and containment
guards are untouched. Surfacing is idempotent (byte-for-byte no-op on repeat).

## Implementation closeout (US-005 — preflight harness-auth probe)

`torture-test/bin/tt-harness-auth-probe` is the fail-closed preflight seam that
turns the US-004 credential surfacing into a GREEN/RED verdict BEFORE any real
case launches. For each requested harness (`pi`/`hermes` — or each real-case
harness enumerated from the tier manifests when none is named) it runs two legs:

1. **PRESENCE** — the enumerated minimal surfaced files exist in the contained
   TT home (pi: `.pi/agent/{settings.json,models.json,auth.json}`; hermes:
   `.hermes/{config.yaml,auth.json}`). A missing file means surfacing never
   happened (or was stripped).
2. **ANSWER** — a trivial one-shot harness invocation under the contained spawn
   env (`pi --print --no-tools --no-session --no-context-files` / `hermes -z`).
   This is the zero/near-zero-token "can actually answer" check: pi's
   `No API key found for the selected model` fails fast with exit 1 BEFORE any
   HTTP request (zero tokens), while the success path is a single tiny
   completion (near-zero tokens — no tool loop, no full agent run).

**Fail-closed reasons** (stderr + non-zero exit): `harness-auth-missing: pi`,
`harness-auth-missing: hermes`, plus the manifest-enumeration reasons
`manifest-unreadable: <name>` / `manifest-invalid: <name>: line <n>` (mirroring
US-002).

**Cheap + contained:** the probe never starts the real daemon (it invokes the
harness binary directly), never writes state (read-only/idempotent), and is
seam-testable via `TT_VAR`, `TT_CASES_DIR`, `TAMANDUA_PI_BINARY` /
`TAMANDUA_HERMES_BINARY` so the self-test
(`torture-test/bin/tt-harness-auth-probe.test.sh`) spends ZERO real tokens.

## Implementation closeout (US-006 — wire harness-auth probe into the preflight chain)

`tt-controller`'s `runRealPreflight` now includes a fourth preflight leg —
`harness-auth` — ordered immediately after `home-provision` (which surfaces the
credentials) and before `catalog-install` / `daemon-up` / real case execution:

1. **Current-selection harness resolution** (`requiredHarnessesFor`): the
   controller computes the DISTINCT real-case harnesses (`pi` / `hermes`) from
   the FILTERED manifest (after `--case`), so a pi-only selection probes `pi`
   and never `hermes`. Scripted (`scripted-pi`/`scripted-hermes`/`execution_mode:
   scripted`) and `local` cases require no harness auth and are skipped.
2. **Conditional leg:** when the required-harness set is non-empty, the
   `tt-harness-auth-probe` helper runs with those harnesses as explicit args
   (no full-tier enumeration). When the selection needs no pi/hermes harness,
   the leg is skipped entirely — keeping the local-harness real-daemon scenario
   (and the US-004 idempotence test) zero-token.
3. **Fail-closed:** a non-zero probe exit persists the DISTINCT detected reason
   (`harness-auth-missing: pi` / `harness-auth-missing: hermes`, read from the
   helper's `REASON:` line) in `state.real_preflight.reason` and aborts the
   campaign non-zero. The leg does not mask the other legs' reasons; the daemon
   teardown still runs in the `finally` path.
4. **Injection seam:** the helper path is overridable via
   `TT_CONTROLLER_PREFLIGHT_AUTH` (mirroring the existing `*_PROVISION` /
   `*_CATALOG` / `*_DAEMON` seams), so the preflight wiring test exercises the
   new leg with a deterministic stub.

**Guard semantics unchanged:** scripted-only selections and
`TT_DRY_RUN_REAL_LAUNCH` dry runs still never engage the preflight (and thus
never run the probe), because `realPreflightRequired` is untouched. The probe
never touches the operator's `~/.tamandua` or the 33xx daemon (it runs under
the contained spawn env and reads only the contained TT home).
