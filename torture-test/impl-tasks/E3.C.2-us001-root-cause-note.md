# E3.C.2 US-001: Root-cause note — why the scripted daemon LAUNCH gets SIGTERM

Story: diagnose which code path signals SIGTERM to the systemd-run daemon
launch during `daemon-control scripted start` (all four w2 scripted
scenarios PRODUCT_FAIL on main after E3.C.1, 74f4d332).

**Diagnosis (one line):** the systemd scope unit name `tamandua-tt-scripted`
(and the ports 5334/5338/5339) are FIXED and shared by every concurrent
run/worktree; daemon-control issues *unconditional* `systemctl --user stop
tamandua-tt-scripted.scope` at three sites, so a concurrent run's stop TERMs
another run's in-flight launch. This is a cross-worktree collision, not a
defect in E3.C.1's new recorded-identity logic.

---

## 1. The exact signalling mechanism

`bin/daemon-control` derives the scope unit name from the kind only:

```bash
local scope_unit="tamandua-tt-$name"      # tamandua-tt-scripted / tamandua-tt-real
```

Every daemon-control invocation, from ANY worktree or checkout, therefore
manages the SAME systemd unit. The tool then stops that unit *by name,
unconditionally*, at three sites:

| Site | Location | What it does |
|---|---|---|
| `cmd_start` pre-launch clear | line 603 | `systemctl --user stop "${scope_unit%.scope}.scope"` before launching (plus `reset-failed`) |
| `cmd_stop` idempotent residual cleanup | line 733 | stops the provenanced scope even on the "already stopped" no-op path |
| `cmd_stop` Step 5 | line 868 | stops the provenanced scope at teardown (plus `reset-failed`) |

`systemctl stop` on a scope sends SIGTERM to every process in the scope. When
run A's daemon-control issues that stop while run B's `systemd-run --user
--scope --unit=tamandua-tt-scripted ...` launch is in flight, B's launch is
TERMinated. Because the launch runs as a *foreground* child of B's
daemon-control bash (`systemd-run ... >/dev/null 2>&1`, no `&`), bash prints
its job-termination report:

```
Terminated                 systemd-run --user --scope --unit="$scope_unit" --quiet env -i ... bash -c "$launch_script" > /dev/null 2>&1
```

and the command's exit status is 128+15=143. `set -e` propagates it and
`run-scripted-scenario`'s `daemon_control start || fail "daemon-control
scripted start failed"` fires (scenarios/lib/run-scripted-scenario:285).

### Why the four scenarios all failed in ~11-15s

The collision is bidirectional and self-sustaining: once a run's launch is
TERMinated, its teardown/next-scenario `cmd_stop`/pre-launch-stop fires the
same unconditional stop, which TERMs the other run's in-flight launch, and so
on. Each failed scenario also leaves the shared ports/pidfile in a contested
state, so subsequent `tamandua daemon start` inside the scope cannot bind
(5334/5338/5339 held by the concurrent worktree's daemon) and the pidfile
never appears — the W2.23a/b/c failures show "start failed" without the
`Terminated` line for exactly this reason (their `systemd-run` completed but
the daemon inside never came up / was stopped before the pidfile appeared).

## 3. Suspect analysis (each explicitly confirmed or ruled out)

### (a) ABA/startTime escalation (`verify_recorded_identity`) — RULED OUT

`verify_recorded_identity` (daemon-control:440) is a fail-closed *guard*: it
REFUSES (returns 1) when the recorded startTime is absent or does not match
the pid's current `/proc` starttime; it never signals anything. It is called
only from `cmd_stop`'s escalation path (lines 804/814) and the lingering-
listener cleanup (line 851) — **never from `cmd_start`**. `cmd_start`
(lines 558-687) contains zero kill/signal sites (only `kill -0` liveness
probes). The failing command is `start`; at launch time no provenance exists
yet (it is written after the pidfile appears, line 670), so an ABA escalation
cannot even be considered. Confirmed not the signal source.

### (b) Self-group wrapper — RULED OUT

daemon-control contains no `setsid`/pgid/process-group manipulation at all
(grep for `group|setsid|pgid` matches only comments and the
`verify_listener_target` pgid-disjoint check). The scripted launch path is a
plain `systemd-run --user --scope` (line 607). The "battery self-group"
assertion lives in the E3.C.1-owned test
`self-tests/tier1-scripted-probe-battery.test.ts`, not in the launch path.
Confirmed not the signal source.

### (c) Inverted staleness comparison — RULED OUT

The only startTime comparisons are equality checks via
`tt-process-identity.mjs --check/--verify` (`verify_recorded_identity`,
`verify_listener_target`); a mismatch REFUSES the signal. No inverted
comparison exists anywhere in daemon-control. Confirmed not the signal
source.

**All three E3.C.1 suspects are ruled out — the signal comes from the
unconditional `systemctl stop` of the shared fixed scope name issued by a
concurrent daemon-control invocation.**

## 4. Reproduction (documented; production 33xx daemon untouched)

The failure mode was reproduced 1:1 on this host (2026-08-17 ~15:31 local)
with a scratch scope using the *actual* fixed name `tamandua-tt-scripted`
(the bare unit was free; worktree 865's live daemon uses the hashed name
`tamandua-tt-scripted-c351c4b5`, which was verified untouched afterwards).
Mimicking `cmd_start` exactly (`set -euo pipefail`, foreground
`systemd-run --user --scope --unit=tamandua-tt-scripted ... >/dev/null 2>&1`),
then issuing the concurrent worktree's `systemctl --user stop
tamandua-tt-scripted.scope`:

```
=== launcher script exit: 143 ===
=== launcher stderr ===
daemon-control: starting scripted daemon...
daemon-control: using systemd scope: tamandua-tt-scripted
Terminated                 systemd-run --user --scope --unit="$scope_unit" --quiet env -i sleep 60 > /dev/null 2>&1
```

Byte-for-byte the campaign's `Terminated` line; exit 143 (SIGTERM) matching
`set -e` propagation. At that point (15:31 local) the bare name was free and
worktree 865's live daemon used the hashed name
`tamandua-tt-scripted-c351c4b5` — verified untouched by the bare-name stop,
demonstrating both the defect and the isolation property the US-002 fix
(PER-WORKTREE derived unit name) provides. Cleanup verified: no
`tamandua-tt-scripted.scope` remained, no processes leaked, live daemon
untouched.

**Live re-enactment during the second run (15:35:53 local, while capturing
output for the evidence file):** the repro's pre-launch stop — again exactly
cmd_start line 603 — ran while worktree 866's campaign was mid-flight on the
same fixed name. The journal records the collision in real time
(`tamandua-tt-scripted.scope`): 866's w2.23c scope Started 15:35:45, Stopping
15:35:53 (7.677s lifetime, cut short by the repro's stop), the repro's own
`sleep 60` scope cycled, and 866 relaunched the scenario at 15:35:54 and
continued (its smoke campaign completed 2/2; the production 33xx daemon was
never touched). The reproduction therefore did not merely mimic the
mechanism — it TERMinated a live concurrent run's in-flight scope, the exact
failure mode, with the journal as evidence. This is why the repro is
hermetic-only in US-003: any daemon-control invocation on the shared fixed
name TERMs whatever scope is live, regardless of which run owns it.

## 5. Why E3.C.1's own bare-tier1 GREEN x2 proof passed — proof-protocol gap

E3.C.1 (74f4d332, committed 14:55:15) verified with bare `./run-torture-test
--tier1` GREEN x2. That proof is GREEN **because the collision is a race that
only manifests when two runs' daemon-control invocations destructively
interleave on the fixed scope name/ports during the proof window** — and the
proof protocol has **no concurrent-run isolation guard**. At the time of the
failure:

- 866's MACP2 campaign (`feature/macp2-pycache-junk-portability`, c34941b1)
  was live at 14:54:56, driving the same bare `tamandua-tt-scripted` scope
  and 5334/5338/5339 ports (its w2.23c scope Started 14:55:43);
- E3.C.1 committed at 14:55:15;
- the failing main campaign started 14:55:44 and hit the collision.

E3.C.1's own proof windows simply did not destructively interleave with the
concurrent campaigns (865/866) — nothing about the proof detects or excludes
concurrent runs sharing the fixed scope/ports. A bare GREEN x2 run on a
machine where another run happens to be mid-stop is still GREEN; the next
run's start can be TERMinated by the same fixed name. **This is a
proof-protocol gap**: the tier1 proof protocol must pin that this worktree's
daemon lifecycle is isolated from concurrent runs (per-worktree scope naming
+ cross-worktree stop isolation), which is exactly the guard US-003 adds
(`self-tests/tier1-daemon-control-scope-isolation.test.ts`).

## 6. Fix direction (for US-002; no production change in this story)

- Derive the scope unit name per worktree: `tamandua-tt-<kind>-<8-hex-cksum
  of TT_REPO_ROOT>` (mirror the T2.1 US-009 pattern live in worktree 865:
  `tamandua-tt-scripted-c351c4b5`), used consistently across cmd_start
  (systemd-run `--unit`, pre-launch stop/reset-failed), cmd_stop Step 5,
  idempotent residual cleanup, provenance `scopeUnit`, and `verify_cgroup`.
- Serialize on the shared fixed ports (bounded port-wait in cmd_start) and
  clear a stale `tamandua.pid` before waiting, so concurrent worktrees
  EADDRINUSE-fail closed instead of racing.
- Preserve every E3.C.1 US-004 piece: IDENTITY_TOOL, verify_recorded_identity,
  verify_listener_target, verify_process_tt_owned, provenance startTime
  recording, production guards, guard_kind_containment — nothing reverted.
