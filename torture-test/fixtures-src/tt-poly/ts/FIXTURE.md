# tt-poly ts/ Subtree Fixture

Expense tracker web app — small HTTP server + static frontend with
vanilla JavaScript. Ported from `torture-test/fixtures-src/tt-ts/`
for the tt-poly five-language storm monorepo.

## Project Overview

- **~1,100 LOC** TypeScript/JavaScript split roughly 60% TS source +
  tests, 40% static frontend JS/CSS/HTML
- **Node.js HTTP server** with REST API — zero external dependencies,
  uses only built-in `node:http`, `node:fs`, `node:crypto`, `node:path`
- **Static frontend** in `public/` — vanilla JavaScript (no framework),
  single HTML page with expense list, add/edit/delete, category filter,
  and total display
- **Data layer** — in-memory `InMemoryStore` class (ES private fields)
  with full CRUD, category/date filtering, and aggregation
- **Zero runtime dependencies** — TypeScript and tsx are dev-only;
  `npm test` works with a fresh `npm install` on any Node.js ≥ 22 host

## Junk Probes

Per spec 02's **two-class junk probe requirement**, this subtree carries
both classes. Neither is gitignored — oracles verify they appear as
untracked in `git status` so the dirty-tree gate tolerates them while
rejecting tracked drift.

### Regenerated Junk

- **`package-lock.json`** — regenerated by `npm install` on every fresh
  clone. Content varies with npm version and platform, so it is never
  committed and never gitignored.

- **`node_modules/` with one stray file** — the `pretest` script
  (`scripts/create-stray.js`) writes a single file
  `node_modules/.tamandua-stray-probe.txt` before each test run. The
  entire `node_modules/` tree is regenerated by `npm install`, is
  never committed, and is never gitignored.

### Inert Operator Junk

- **`operator-notes.local`** — planted at fixture instantiation with a
  fixed byte string. Never touched by any tool, `npm install`, or test
  run for the entire campaign.

| POLY-BUG-T2 | A2 (two-module) | Date handling | Medium | Date parsing in `server.ts` (local-time `new Date()`) mismatches `store.ts` string-comparison filtering — expenses near day boundaries are missed in date-range queries. Fix requires coordinated changes in both modules. |

## Seeded Features (POLY-FEAT-T1..T4)

Feature backlog for feature-dev workflow scenarios. Each feature has a
stable ID, flavor tag (frontend/backend), description, and clear acceptance
boundaries. Two features are frontend-flavored (FEAT-T1, FEAT-T2) and
two are backend/API-focused (FEAT-T3, FEAT-T4). This backlog matches the
`torture-test/fixtures-src/tt-ts/` feature backlog. These features are
**documentation only** — no seed patches exist for features.

| ID | Flavor | Description | Acceptance Boundaries |
|----|--------|-------------|-----------------------|
| `POLY-FEAT-T1` | Frontend | **Custom expense categories management** — admin UI panel to add new categories, remove unused categories, and rename existing categories (with migration of existing expenses to the new name). Updates `public/index.html`, `public/app.js`, and `public/style.css`. | Category changes persist across page reloads (stored in server memory — no database, via `InMemoryStore` in `src/store.ts`). New categories appear in the add/edit form dropdown immediately. Removing a category that has expenses is rejected with a user-visible error. Renaming a category updates all expenses with the old name via `store.updateCategory()`. UI is accessible (standard form controls). Existing store tests must still pass. |
| `POLY-FEAT-T2` | Frontend | **Monthly expense dashboard with bar chart visualization** — a `/dashboard` page (or section) showing spending by category per month as a bar chart (canvas-drawn in `public/app.js`, no chart library). Includes month selector (previous/next navigation) and category breakdown legend. Adds a `store.getCategoryTotalsByMonth(month: string)` method to `src/store.ts`. | Dashboard displays total for each category as a bar proportional to the largest category. Zero-value categories are not shown. Month navigation works for any month with expense data. Bar chart is drawn with Canvas API (no external dependency). Empty months show a "No expenses for this month" message. Month selector uses semantic `<` and `>` buttons with a label showing the current month/year. |
| `POLY-FEAT-T3` | Backend | **Expense CSV export** — endpoint `GET /api/expenses/export` in `src/server.ts` that returns expense data as CSV (`text/csv` Content-Type). Includes a "Download CSV" button in `public/index.html` that triggers a file download via `public/app.js`. CSV columns: id, description, amount, category, date. | Endpoint returns valid CSV with header row and one row per expense. Amounts are formatted as plain numbers (no currency symbol). CSV is UTF-8 encoded. Endpoint respects the active category filter from the query string. Download button triggers browser file download with filename `expenses-<YYYY-MM-DD>.csv`. Categories and descriptions containing commas or quotes are properly CSV-escaped. No external CSV library — implement escaping manually for portability. |
| `POLY-FEAT-T4` | Backend | **Recurring monthly expense support** — expenses can be flagged as `recurring: true` via a checkbox in the add/edit form (`public/index.html`). On server start (or via a new `POST /api/expenses/recurring/generate` endpoint in `src/server.ts`), the system auto-generates an expense instance for the current month for each recurring expense that hasn't been generated yet this month. Recurring expenses show a "🔄" indicator in the list. | Recurring flag is stored on the expense object via `InMemoryStore` in `src/store.ts` and preserved across edits. Auto-generation creates exactly one instance per recurring source per calendar month (idempotent — calling generate twice in the same month produces no duplicates, verified via `store.hasGeneratedForMonth()`). Generated instances have the current date, same description/amount/category as the source, and are NOT themselves marked recurring (only the source is). The source recurring expense's date column shows the original creation date, not the generation date. A manually deleted generated instance is NOT regenerated within the same month. |

## Cross-Language Integration Bug (POLY-BUG-A5)

A5 archetype — spans the python/ and ts/ subtrees. The fix in one subtree
breaks the other subtree's test — union-of-merges bait for the storm.

| ID | Archetype | Difficulty | Modules | Symptom / Description |
|----|-----------|------------|---------|-----------------------|
| `POLY-BUG-A5` | A5 — cross-language integration | medium | `python/src/schedlib/integrations.py`, `ts/src/server.ts` | `integrations.py` exports a `lookup_calendar_name()` function that returns a dict with `{\"name\": str, \"id\": int}`. `ts/src/server.ts` imports/calls this function via a test-only bridge and expects `{name: string, id: number}`. The seed changes the Python function signature to return `{\"calendar_name\": str, \"calendar_id\": int}`, AND changes the TS bridge to expect `{calendar_name, calendar_id}` — both subtrees are modified. Fixing only python/ or only ts/ leaves one subtree's test failing — the partial-fix property is cross-language. |

`seed/POLY-BUG-A5` ref lives in the golden bare repo (green base + the
two-file coordinated change). Fix patch at `seeds/POLY-BUG-A5/fix.patch`.
For the python/ subtree, see `python/FIXTURE.md` for the reciprocal documentation.

## Archetype Reference

| Archetype | Name | Signature |
|-----------|------|-----------|
| A1 | Off-by-one | Logic error producing wrong output; no existing test catches it — fixer must write the regression test |
| A2 | Two-module | Bug spans two modules; fix requires coordinated changes in both files, not a single-line patch |
| A3 | Red-herring | Visible symptom points to module X (e.g., frontend), but root cause is in module Y (e.g., store) |

## Integrity Invariants

1. **Baseline green:** `npm test` exits 0 on the pristine tree (59 pass,
   0 fail)
2. **Seed isolation:** each seed patch applies cleanly via `git apply` to
   baseline; no seed depends on another seed's state
3. **Fix correctness:** each fix patch restores green when applied on
   top of its seed
4. **Junk presence:** `package-lock.json` and `node_modules/` exist and
   are untracked after `npm install && npm test`
5. **Inert junk integrity:** `operator-notes.local` is byte-identical to
   the fixture source (provisioning) reference
6. **Deterministic builds:** two consecutive runs of `build-golden.sh`
   produce identical commit hashes
