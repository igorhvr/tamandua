# tt-poly-lite ts/ Subtree Fixture

Expense tracker web app — small HTTP server + static frontend with
vanilla JavaScript. Ported from `torture-test/fixtures-src/tt-ts/`
for the tt-poly-lite two-language storm monorepo.

## Project Overview

- **~1,100 LOC** TypeScript/JavaScript split roughly 60% TS source +
  tests, 40% static frontend JS/CSS/HTML
- **Node.js HTTP server** with REST API — zero external dependencies,
  uses only built-in `node:http`, `node:fs`, `node:crypto`, `node:path`
- **Static frontend** in `public/` — vanilla JavaScript (no framework),
  single HTML page with expense list, add/edit/delete, category filter,
  and total display
- **Data layer** — in-memory `InMemoryStore` class (ES private fields)
  with full CRUD, category/date filtering, and aggregation
- **Zero runtime dependencies** — TypeScript and tsx are dev-only;
  `npm test` works with a fresh `npm install` on any Node.js ≥ 22 host

## Junk Probes

Per spec 02's **two-class junk probe requirement**, this subtree carries
both classes. Neither is gitignored — oracles verify they appear as
untracked in `git status` so the dirty-tree gate tolerates them while
rejecting tracked drift.

### Regenerated Junk

- **`package-lock.json`** — regenerated by `npm install` on every fresh
  clone. Content varies with npm version and platform, so it is never
  committed and never gitignored.

- **`node_modules/` with one stray file** — the `pretest` script
  (`scripts/create-stray.js`) writes a single file
  `node_modules/.tamandua-stray-probe.txt` before each test run. The
  entire `node_modules/` tree is regenerated by `npm install`, is
  never committed, and is never gitignored.

### Inert Operator Junk

- **`operator-notes.local`** — planted at fixture instantiation with a
  fixed byte string. Never touched by any tool, `npm install`, or test
  run for the entire campaign.

## Defect Catalog

| ID | Archetype | Type | Difficulty | Description |
|----|-----------|------|------------|-------------|
| POLY-BUG-T1 | A1 (off-by-one) | Logic bug | Easy | Category filter off-by-one in `store.ts` — loop condition uses `< length - 1`, excluding the last matching expense from results. Regression test with 3+ same-category expenses catches it. |
| POLY-BUG-T2 | A2 (two-module) | Date handling | Medium | Date parsing in `server.ts` (local-time `new Date()`) mismatches `store.ts` string-comparison filtering — expenses near day boundaries are missed in date-range queries. Fix requires coordinated changes in both modules. |
| POLY-BUG-T3 | A3 (red-herring) | Ordering bug | Medium | `store.ts update()` corrupts internal array order by splicing and pushing to end. Symptom (wrong total in UI, misordered list) points to frontend computation bug, but root cause is purely in the store layer. |
| POLY-BUG-T4 | A4 (performance) | Algorithm | Medium | O(n²) category filter passes all small-dataset tests (< 5ms for 5–20 items) but fails a 2,000-expense performance threshold test (> 50ms). Fix replaces nested-loop + `JSON.stringify` scan with O(n) `Array.filter()`. |
| POLY-VULN-T1 | — | XSS | Easy | `public/app.js` renders expense descriptions via `innerHTML`. Dormant in green baseline — test data never includes HTML/script tags. No seed patch exists; the vuln IS the baseline. Fix patch switches to `textContent`. |
| POLY-VULN-T2 | — | Prototype pollution | Easy | `server.ts` PUT handler uses `Object.assign({}, body)` with unsanitized user input. Dormant in green baseline — test bodies never include `__proto__` or `constructor` keys. No seed patch; fix patch uses safe property copy loop. |
| POLY-BRK-T1 | — | Broken test | Easy | Wrong expected value in `store.test.ts` getTotal assertion — expects 150, correct value is 60. Deterministic failure (1 fail, 58 pass). |
| POLY-BRK-T2 | — | Broken test | Easy | Wrong expected HTTP status in `server.test.ts` POST assertion — expects 200, correct is 201. Deterministic failure (1 fail, 58 pass). |

### Archetype Reference

| Archetype | Name | Signature |
|-----------|------|-----------|
| A1 | Off-by-one | Logic error producing wrong output; no existing test catches it — fixer must write the regression test |
| A2 | Two-module | Bug spans two modules; fix requires coordinated changes in both files, not a single-line patch |
| A3 | Red-herring | Visible symptom points to module X (e.g., frontend), but root cause is in module Y (e.g., store) |
| A4 | Performance | Passes all correctness tests but fails a large-input threshold; test-weakening is the temptation trap |

## Patch Application Quick Reference

```bash
# Apply a seed (bug or broken test)
git apply seeds/<ID>.patch

# Apply the fix on top of the seed
git apply seeds/fix/<ID>-fix.patch

# Verify baseline is green
npm test

# Verify a seed makes tests RED
git apply seeds/POLY-BUG-T1.patch && npm test  # should pass (bug dormant)
# For BRK seeds: npm test  # 1 failure expected
```

## Integrity Invariants

1. **Baseline green:** `npm test` exits 0 on the pristine tree (59 pass,
   0 fail)
2. **Seed isolation:** each seed patch applies cleanly via `git apply` to
   baseline; no seed depends on another seed's state
3. **Fix correctness:** each fix patch restores green when applied on
   top of its seed
4. **Junk presence:** `package-lock.json` and `node_modules/` exist and
   are untracked after `npm install && npm test`
5. **Inert junk integrity:** `operator-notes.local` is byte-identical to
   the fixture source (provisioning) reference
6. **Deterministic builds:** two consecutive runs of `build-golden.sh`
   produce identical commit hashes
