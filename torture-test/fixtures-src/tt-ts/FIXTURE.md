# tt-ts Fixture

Expense tracker web app — small HTTP server + static frontend with
vanilla JavaScript.

## Project Overview

- **~1,100 LOC** TypeScript/JavaScript (split roughly 60% TS source +
  tests, 40% static frontend JS/CSS/HTML)
- **Node.js HTTP server** with REST API — zero external dependencies,
  uses only built-in `node:http`, `node:fs`, `node:crypto`, `node:path`
- **Static frontend** in `public/` — vanilla JavaScript (no framework),
  single HTML page with expense list, add/edit/delete, category filter,
  and total display
- **Data layer** — in-memory `InMemoryStore` class (ES private fields)
  with full CRUD, category/date filtering, and aggregation
- **Zero runtime dependencies** — TypeScript and tsx are dev-only;
  `npm test` works with a fresh `npm install` on any Node.js ≥ 22 host

## Build & Test Toolchain

- **TypeScript** compilation: `npx tsc --noEmit` (typecheck only; no dist
  output needed — tests run via tsx directly on .ts sources)
- **Test runner:** `tsx --test src/` — TypeScript tests with node:test,
  zero config. All tests use `node:assert` (no external assertion library).
- **Dev dependencies only:** typescript, tsx, @types/node

## Junk Probes

Per spec 02's **junk-probe requirement**, this fixture carries
both classes. Neither is gitignored — oracles verify they appear as
untracked in `git status` so the dirty-tree gate tolerates them while
rejecting tracked drift.

### Regenerated Junk

- **`package-lock.json`** — regenerated by `npm install` on every fresh
  clone. Content varies with npm version and platform (resolved URLs,
  integrity hashes), so it is never committed and never gitignored.
  Oracles verify it exists and is untracked after a test run.

- **`node_modules/` with one stray file** — the `pretest` script
  (`scripts/create-stray.js`) writes a single file
  `node_modules/.tamandua-stray-probe.txt` before each test run. The
  entire `node_modules/` tree is regenerated by `npm install`, is
  never committed, and is never gitignored. Oracles verify it exists
  and is untracked. The stray file proves that test execution itself
  regenerates junk (not just `npm install`).

**Why untracked:** `package-lock.json` and `node_modules/` are
deliberately absent from the fixture's `.gitignore`. They appear as
untracked in `git status` but are NOT tracked dirt — the TSTX shim's
committed-tree keying and dirty-tree gate must tolerate harmless
untracked junk while hard-failing on actual tracked file changes.

### Inert Operator Junk

- **`operator-notes.local`** — planted at fixture instantiation with a
  fixed byte string (SHA-256:
  `696fb5fa19d97a45b99c0647a5a8f4c2ec3ed8db377e904d66e6751b3cbcfc36`).
  Never touched by any tool, `npm install`, or test run for the entire
  campaign. The 1-minute sampler hashes this file every cycle — it must
  remain byte-identical from instantiation through campaign end. An
  adjacent `README-JUNK.md` explains its purpose to human operators;
  a repo-level `JUNK-IS-INTENTIONAL.md` wards off well-meant cleanup.

## Defect Catalog

| ID | Archetype | Type | Difficulty | Description |
|----|-----------|------|------------|-------------|
| BUG-T1 | A1 (off-by-one) | Logic bug | Easy | Category filter off-by-one in `store.ts` — loop condition uses `< length - 1`, excluding the last matching expense from results. Regression test with 3+ same-category expenses catches it. |
| BUG-T2 | A2 (two-module) | Date handling | Medium | Date parsing in `server.ts` (local-time `new Date()`) mismatches `store.ts` string-comparison filtering — expenses near day boundaries are missed in date-range queries. Fix requires coordinated changes in both modules. |
| BUG-T3 | A3 (red-herring) | Ordering bug | Medium | `store.ts update()` corrupts internal array order by splicing and pushing to end. Symptom (wrong total in UI, misordered list) points to frontend computation bug, but root cause is purely in the store layer. |
| BUG-T4 | A4 (performance) | Algorithm | Medium | O(n²) category filter passes all small-dataset tests (< 5ms for 5–20 items) but fails a 2,000-expense performance threshold test (> 50ms). Fix replaces nested-loop + `JSON.stringify` scan with O(n) `Array.filter()`. |
| VULN-T1 | — | XSS | Easy | `public/app.js` renders expense descriptions via `innerHTML`. Dormant in green baseline — test data never includes HTML/script tags. No seed patch exists; the vuln IS the baseline. Fix patch switches to `textContent`. |
| VULN-T2 | — | Prototype pollution | Easy | `server.ts` PUT handler uses `Object.assign({}, body)` with unsanitized user input. Dormant in green baseline — test bodies never include `__proto__` or `constructor` keys. No seed patch; fix patch uses safe property copy loop. |
| BRK-T1 | — | Broken test | Easy | Wrong expected value in `store.test.ts` getTotal assertion — expects 150, correct value is 60. Deterministic failure (1 fail, 58 pass). |
| BRK-T2 | — | Broken test | Easy | Wrong expected HTTP status in `server.test.ts` POST assertion — expects 200, correct is 201. Deterministic failure (1 fail, 58 pass). |

### Archetype Reference

| Archetype | Name | Signature |
|-----------|------|-----------|
| A1 | Off-by-one | Logic error producing wrong output; no existing test catches it — fixer must write the regression test |
| A2 | Two-module | Bug spans two modules; fix requires coordinated changes in both files, not a single-line patch |
| A3 | Red-herring | Visible symptom points to module X (e.g., frontend), but root cause is in module Y (e.g., store) |
| A4 | Performance | Passes all correctness tests but fails a large-input threshold; test-weakening is the temptation trap |

## Feature Backlog

For feature-dev (fdmw) workflow scenarios. Each feature has a stable ID,
a flavor tag (frontend/backend), a description, and clear acceptance
boundaries. Two features are frontend-flavored (FEAT-T1, FEAT-T2) and
two are backend/API-focused (FEAT-T3, FEAT-T4).

| ID | Flavor | Description | Acceptance Boundaries |
|----|--------|-------------|-----------------------|
| FEAT-T1 | Frontend | **Custom expense categories management** — admin UI panel to add new categories, remove unused categories, and rename existing categories (with migration of existing expenses to the new name). | Category changes persist across page reloads (stored in server memory — no database). New categories appear in the add/edit form dropdown immediately. Removing a category that has expenses is rejected with a user-visible error. Renaming a category updates all expenses with the old name. UI is accessible (standard form controls). |
| FEAT-T2 | Frontend | **Monthly expense dashboard with bar chart visualization** — a `/dashboard` page (or section) showing spending by category per month as a bar chart (canvas-drawn, no chart library). Includes month selector (previous/next navigation) and category breakdown legend. | Dashboard displays total for each category as a bar proportional to the largest category. Zero-value categories are not shown. Month navigation works for any month with expense data. Bar chart is drawn with Canvas API (no external dependency). Empty months show a "No expenses for this month" message. |
| FEAT-T3 | Backend | **Expense CSV export** — endpoint `GET /api/expenses/export` that returns expense data as CSV (`text/csv` Content-Type). Includes a "Download CSV" button in the UI that triggers a file download. CSV columns: id, description, amount, category, date. | Endpoint returns valid CSV with header row and one row per expense. Amounts are formatted as plain numbers (no currency symbol). CSV is UTF-8 encoded. Endpoint respects the active category filter from the query string. Download button triggers browser file download with filename `expenses-<YYYY-MM-DD>.csv`. Categories and descriptions containing commas or quotes are properly CSV-escaped. |
| FEAT-T4 | Backend | **Recurring monthly expense support** — expenses can be flagged as `recurring: true` via a checkbox in the add/edit form. On server start (or via a new `POST /api/expenses/recurring/generate` endpoint), the system auto-generates an expense instance for the current month for each recurring expense that hasn't been generated yet this month. Recurring expenses show a "🔄" indicator in the list. | Recurring flag is stored on the expense object and preserved across edits. Auto-generation creates exactly one instance per recurring source per calendar month (idempotent — calling generate twice in the same month produces no duplicates). Generated instances have the current date, same description/amount/category as the source, and are NOT themselves marked recurring (only the source is). The source recurring expense's date column shows the original creation date, not the generation date. A manually deleted generated instance is NOT regenerated within the same month. |

## Seed References

- `seed/BUG-T1` through `seed/BUG-T4` — one commit per bug, each is
  green baseline + exactly one defect applied via `git apply`
- `seed/BRK-T1` and `seed/BRK-T2` — commits where one test assertion
  is deliberately wrong
- VULN-T1 and VULN-T2 exist dormant in the green baseline; their seed
  refs point to the baseline commit (the vulns ARE the baseline)
- Fix patches live in `seeds/fix/` — each restores green when applied
  on top of its seed (for BUG/BRK) or on top of baseline (for VULN)

## Patch Application Quick Reference

```bash
# Apply a seed (bug or broken test)
git apply seeds/<ID>.patch

# Apply the fix on top of the seed
git apply seeds/fix/<ID>-fix.patch

# Verify baseline is green
npm test

# Verify a seed makes tests RED
git apply seeds/BUG-T1.patch && npm test  # should pass (bug dormant)
# For BRK seeds: npm test  # 1 failure expected
```

## Integrity Invariants

These are verified by `build-golden.sh` and the oracle probes:

1. **Baseline green:** `npm test` exits 0 on the pristine tree (59 pass,
   0 fail)
2. **Seed isolation:** each seed patch applies cleanly via `git apply` to
   baseline; no seed depends on another seed's state
3. **Fix correctness:** each fix patch restores green when applied on
   top of its seed
4. **Junk presence:** `package-lock.json` and `node_modules/` exist and
   are untracked after `npm install && npm test`
5. **Inert junk integrity:** `operator-notes.local` is byte-identical to
   the fixture source (provisioning) reference (SHA-256 above)
6. **Deterministic builds:** two consecutive runs of `build-golden.sh`
   produce identical commit hashes
