# W4.21: Bare non-interactive PATH — full launch (daemon + one bfmw), never silent worker_lost loops (scripted, zero tokens; gating)

Scripted local-command case (zero tokens): the scenario cell
`scenarios/w4.21/bare-noninteractive-launch/` performs a FULL launch
(contained daemon + one bug-fix-merge-worktree run) from a **bare
non-interactive shell** constructed with `env -i` (spec 08 §H W4.21 —
"Full launch (daemon + one bfmw) from a bare non-interactive shell (no
node/pi/hermes on PATH — env -i constructed if the host's default shells
are rich)"). The discovery corridor must produce a working run OR a
diagnosable refusal — **never silent worker_lost loops**.

## Host-adaptation predicate (documented choice)

- `requires.platform = "linux"`: the `env -i` bare-shell construction and
  the launcher PATH-resolution corridor are authored and validated on linux
  (the tier0 cell platform). Spec 01's platform-facts table links W4.21 to
  the darwin BSD-userland/shell-string defect class; this corridor does NOT
  exercise shell-string quoting (the launcher is a plain `exec node`), so
  the linux-authored cell is the honest host adaptation — a darwin host
  gates `NOT_RUN (predicate)` with evidence, never a silent skip.
- The standard cell shape: `capabilities ["node-sqlite"]`,
  `containment ["systemd-user-scope"]`, `node_min 22`.

## What the scenario actually exercises (per spec)

The runner builds a scratch origin (`git init -b main` + baseline commit,
the W4.11 scratch-origin shape) and constructs TWO bare non-interactive
shells via `env -i`:

- **Branch A — "rich default shell" (node reachable):** `env -i` with
  PATH rebuilt to the node bin dir + `/usr/bin:/bin` (node found; pi/hermes/
  dsh NOT on the PATH — the runner self-verifies `command -v pi|hermes|dsh`
  fail in that PATH). From that bare shell, the full launch runs:
  `tamandua workflow run <scenario bfmw copy> ... --worktree-origin-repository
  <scratch-origin> --worktree-origin-ref main --wait --json` against the
  contained scripted daemon (scripted-pi behaviors, zero tokens). Expected:
  the run COMPLETES (`status completed`) with zero tokens and NO
  `worker_lost` events — the discovery tiers produce a working run.
- **Branch B — truly bare PATH (node NOT reachable):** `env -i` with PATH
  pointing at a scratch bin that carries the launcher's coreutils
  (`readlink`, `dirname`) but NOT `node` (self-verified via
  `command -v node` in that PATH). The same full-launch argv is invoked from
  that bare shell. Expected: a DIAGNOSABLE REFUSAL at the launcher — exit
  non-zero with `stderr` naming the missing `node` — and NO run row created
  in the contained DB, NO worker_lost events, NO half-registered state
  (the refusal happens before node ever starts, so nothing is claimed and
  nothing can loop).

## Expected

- The scenario cell runs PASS (exit 0) with `caps.tokens = 0` — zero
  tokens, no real pi/hermes/dsh invocation.
- Branch A: the bfmw run completes; `runs.tokens_spent` stays 0; the
  contained DB carries exactly the scenario's own runs (cleaned up after
  capture).
- Branch B: the launch refuses at the launcher with the missing tool named;
  the DB run set is unchanged; zero worker_lost / zero re-pend loops.
- The contained scripted daemon is left stopped; ports 5334/5338/5339 free.

## Boundaries

- The cell writes ONLY under `torture-test/var/` (the scratch origin, the
  bare-shell scratch PATH, the workdirs); `env/tt-env.sh` and the real HOME
  are never touched.
- The bfmw copy is the scenario's installed workflow copy
  (`TT_SCENARIO_WORKFLOW_ID`) with materialized scripted behaviors —
  campaign machinery, never manifest content.
