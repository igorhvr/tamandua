# W4.11: SIGKILL / Ctrl-C `workflow run` launch-violence matrix (scripted, zero tokens; gating)

Scripted local-command case (zero tokens): the scenario cell
`scenarios/w4.11/sigkill-launch-matrix/` exercises spec 08 §C W4.11 — SIGKILL
and Ctrl-C (SIGINT to the launch process GROUP) against `workflow run`
mid-launch — on the CONTAINED scripted daemon. **The most common signal any
user ever sends tamandua is exercised nowhere else; the CLI waiter has no
SIGINT handler in source** — this case pins the aftermath.

## What the scenario actually exercises (per spec arm)

The runner launches real `workflow run` invocations (bug-fix-merge-worktree
worktree-mode copy + a do-now direct-mode copy for the pre-INSERT arm) and
holds each at a deterministic phase marker (a PATH git wrapper pausing
specific git calls — the pre-INSERT arm uses the direct-mode launch's first
git call, which runs before the INSERT), then delivers the signal to the
WHOLE launch process group (`kill -9 -pgid` / `kill -INT -pgid` — the
mechanical core of a real terminal Ctrl-C, which also hits just-spawned
children):

- **SIGKILL (a) before the run INSERT** — held at the DIRECT-mode launch's
  first git call (`git rev-parse --abbrev-ref HEAD`, the original-branch
  capture — worktree-mode launches touch git only AFTER the INSERT, so a
  direct-mode do-now launch is used for this arm): NO run row, NO worktree
  row, nothing claimed on stderr (DC9: "run id on stderr where it existed" —
  it did not exist).
- **SIGKILL (b) during `git worktree add`** — held inside the worktree-add
  call: run row exists (`pending_register`), `run_worktrees` row `creating`,
  the id WAS claimed on stderr (DC9), the worktree is ABSENT (the held add
  never ran real git) — prunable-or-absent holds; no zombie.
- **SIGKILL (c) before registration** — held at the tested-tree rev-parse
  after the worktree exists: run row `pending_register`, `run_worktrees`
  `ready`, the worktree EXISTS and is PRUNABLE (`git worktree remove --force`
  succeeds), steps not yet inserted, never registered.
- **Ctrl-C (d) pre-registration** — held at worktree-add, group SIGINT: the
  launch dies by SIGINT (no handler), the run row SURVIVES with the id printed
  (DC9), and the daemon reconciler takes ownership within one tick
  (scheduling_status leaves `pending_register`) — **the run continues
  detached, NEVER a half-registered orphan**.
- **Ctrl-C (e) during daemon auto-start** — daemon stopped first; the launch
  auto-starts it (spawned DETACHED); group SIGINT on the daemon pidfile: the
  **daemon survives (full-detach proof)** and the run continues detached — a
  step is claimed by the auto-started daemon's reconciler+dispatch.
- **Ctrl-C (f) during `--wait`** — run live and dispatching; group SIGINT to
  the waiter: the waiter dies by SIGINT (exit 130 semantics — no handler in
  source) and **the run continues detached and keeps progressing** — the
  waiter's exit code distinguishes "interrupted, run continues" from failure.

Every arm asserts **no permanent zombie** (the killed process group is fully
reaped) and leaves its own runs deleted from the contained ledger.

## Spec-vs-machinery notes (documented, not silent)

- The spec's Ctrl-C arms are "from a controlling PTY"; the scripted arm
  delivers SIGINT to the launch process GROUP directly (`kill -INT -pgid`).
  The process-group semantics (a real Ctrl-C hits just-spawned children,
  including the held git wrapper) are preserved; the PTY allocation itself is
  a terminal-input detail not needed to pin the product's signal handling.
- The scenario's `workflow run` launches use the CONTAINED scripted daemon
  (control port 5339) and its scripted agents (behaviors file); the run rows
  are this scenario's own and are deleted after capture. Zero tokens.
- W4.11's SIGINT arms pin the spec contract (continue-detached-or-clean-abort
  pre-registration; daemon survives auto-start; waiter exit distinguishes
  interruption); the full registration/recovery machinery observed here is the
  product's own reconciler + detached daemon spawn.
