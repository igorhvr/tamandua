# W4.47: Auth expiry on the copy (REAL pi do-now, small tokens)

The TT env carries COPIED pi credentials at `$TT_HOME/.pi` (provisioned by
bin/tt-provision-home from the operator's `~/.pi`: `agent/settings.json`,
`agent/models.json`, `agent/auth.json`, ...). Mid-wave, the OPERATOR
INVALIDATES the COPIED credentials (e.g. replace `$TT_HOME/.pi/agent/auth.json`
with an invalid/expired token — never touching the REAL `~/.pi`), launches a
do-now, RESTORES the copy, launches again.

## The pinned contract (spec 08 §K W4.47)

- The auth failure surfaces as a DIAGNOSABLE provider/auth error NAMING the
  harness (pi) — NEVER a silent zero-token "completion".
- NEVER a fallback to the REAL `~/.pi`: that fallback would be an
  isolation-breach S0. **O15** (production untouchedness, the campaign-level
  W0/W6 oracle — NOT a per-case oracle, deliberately not declared in the
  manifest) asserts the real credential file's atime/audit trail shows NO
  access during the invalidated window.
- Post-restore launch is CLEAN (the run completes).

## Expected

Diagnosable auth error naming pi while the copy is invalidated; zero real
`~/.pi` access (O15); clean launch after restore. Small real do-now spend
(`caps.tokens` 200k — the do-now unit; the invalidated launch spends ~0).

The manifest row declares fixture `tt-ts` (the do-now runs against the
tt-ts work clone; the seeded content is irrelevant to the auth corridor —
the credential invalidation/restore IS the corridor).

## Operator choreography (machinery delta — documented in tier2-traceability.md)

The invalidation/restore is an OPERATOR action in the task text (there is no
controller op for corrupting the copied credentials); the O15 real-credential
untouchedness check is the campaign-level W0/W6 oracle, recorded here as the
required backstop.

## Boundaries

- The REAL `~/.pi` is READ-ONLY for this case (probed via atime/audit — O15);
  only `$TT_HOME/.pi` (the contained copy) is ever written.
