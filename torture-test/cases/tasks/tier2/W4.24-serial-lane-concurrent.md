# W4.24: Product's own `npm test` serial lane concurrent with 2 TT runs — no cross-talk (scripted, zero tokens; gating)

Scripted local-command case (zero tokens): the scenario cell
`scenarios/w4.24/serial-lane-concurrent/` runs the PRODUCT's own serial test
lane (`scripts/run-serial-tests.sh` — the serial lane of the tamandua
product's `npm test`) on the host CONCURRENTLY with two contained scripted
TT runs (spec 08 §H W4.24 — "Product's own `npm test` serial lane on the
host while 2 TT runs execute. Lane deadline behavior documented; TT runs
unaffected; no cross-talk").

## Host-adaptation predicate (documented choice)

- `requires.platform = "linux"` + `capabilities ["node-sqlite"]` +
  `containment ["systemd-user-scope"]` + `node_min 22`: the standard
  zero-token cell shape (the serial lane and the contained scripted daemon
  are linux-validated machinery).
- The spec's W4.24 predicate column is "—" (runs everywhere the campaign
  does); the cell needs a buildable product tree (the repo checkout) and a
  sqlite-capable node.

## What the scenario actually exercises (per spec)

The runner:

1. **Builds the product tree** (`npm run build` from the repo root — the
   serial lane tests import from `dist/`; the build is SEQUENTIAL, before the
   concurrent corridor, so it is not part of the no-cross-talk window).
2. **Launches two contained scripted TT runs CONCURRENTLY** — two
   `workflow run <scenario bfmw copy>` invocations (distinct scratch origins,
   the W4.11 scratch-origin shape) on the contained scripted daemon
   (scripted-pi behaviors, zero tokens).
3. **Launches the product serial lane CONCURRENTLY** —
   `bash scripts/run-serial-tests.sh` from the repo root under a CLEANED
   host env (all `TT_*`/`TAMANDUA_*` variables stripped, HOME set to the
   operator's account home — the product lane gets a pristine developer env,
   never the contained TT env; `run-serial-tests.sh` sets its own
   `TAMANDUA_TEST_GUARD`/`TAMANDUA_PI_BINARY`/`TAMANDUA_DSH_BINARY`).
   `NODE_TEST_CONTEXT` is ALSO stripped: if it is present (even empty, e.g.
   carried by the controller's operator env), the lane's `node --test`
   prints "node:test run() is being called recursively within a test file.
   skipping running files." and exits 0 in ~75s WITHOUT running the 143
   serial files — the corridor would be silently unexercised. Stripping it
   restores the full ~16-min lane (node --test sets NODE_TEST_CONTEXT itself
   for its workers). The runner's final output is COMPACT single-line JSON so
   tt-controller's local-case summary parser reads the scenario result.
4. **Waits for the TT runs first** (they complete in ~1 min), asserting they
   completed WHILE the serial lane was still running (timestamp overlap —
   the concurrency proof), then waits for the serial lane.

## Daemon-down recovery (T2.1 US-008 — premise correction)

**Premise corrected:** the cell previously assumed the contained scripted
daemon stays up for the whole corridor. On a shared host it can be killed
mid-run by a CONCURRENT campaign: `bin/daemon-control` starts the scripted
daemon inside a FIXED per-user systemd scope unit name `tamandua-tt-scripted`,
and its `cmd_start` clean-slate step runs `systemctl --user stop
tamandua-tt-scripted.scope` — which SIGTERMs WHATEVER daemon currently owns
that scope, including a sibling worktree's live daemon. That is exactly the
operator-campaign failure (campaign-20260816T235948135Z): W4.24's daemon
(PID 55431, started 00:03:50Z) was SIGTERM'd at 00:04:45Z, ONE second after a
concurrent campaign in worktree 862-c9ab2422 ran `daemon-control scripted
start`; the TT run stalled at 4/6 steps and `workflow run --wait --timeout 6m`
timed out (exit 2), so the `completedRunId` assertion (`strictEqual 2 vs 0`)
failed with the wait's `run ... is 'running' but the daemon is down — it may
be stalled` warning.

**Fix (cell orchestration, zero product changes, no assertion weakened):**
while the two TT runs are in flight the runner watches the contained scripted
daemon (the same pid-file + signal-0 liveness check the product's wait uses)
and, on a DOWN window, restarts it via `daemon-control scripted start`
(`scenarios/lib/scripted-daemon-recovery.mjs`). The product's reconciler
re-admits `running` runs and requeues dead-worker steps on its first tick
after daemon start, so the stalled runs RESUME and reach `completed` — the
run-recovery path the `completedRunId` assertion depends on. Every down
window + restart is recorded in the single-line summary (`daemon_recovery`),
and the cell pins that every recorded window closed before the runs could
complete. If the daemon never comes back (recovery bound exhausted) the runs
time out and the cell fails honestly — the corridor assertions are untouched.

**Premise correction (worker_lost_count):** the `worker_lost_count === 0`
assertion ("TT runs unaffected") is scoped to the CONCURRENT-LANE
no-cross-talk corridor — the lane never disrupts the TT runs, so without a
daemon-down window the strict 0 holds unchanged. ACROSS a daemon-down window
a worker loss is EXPECTED and IS the recovery mechanism: the step claimed by
the dead daemon's worker is recovered by the product's dead-worker sweep on
daemon restart (`step.worker_lost`, `worker_lost_count +1`). The assertion is
therefore conditional — strict 0 without a window, non-negative-integer
validation (recorded as `daemon_recovery.worker_lost_counts` in the summary,
never a cross-talk signal) across one — and the runs must still complete with
zero tokens.

## Boundaries

- The cell writes ONLY under `torture-test/var/` (scratch origins,
  workdirs) plus the product build artifacts (`dist/`, `node_modules/` —
  gitignored repo files the product build itself manages); `env/tt-env.sh`
  and the real HOME are never touched by the TT side.
- The product lane runs with a CLEANED env — the no-cross-talk corridor IS
  the assertion that the product suite's own isolation holds regardless of
  the ambient TT env.
- The two TT runs are deleted after capture (the W4.11 scoped-ledger
  pattern) so the contained DB stays scoped to the scenario.
