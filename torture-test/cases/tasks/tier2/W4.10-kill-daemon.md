## Injection (typed chaos — kill-daemon) + operator restart seam

The manifest carries the typed chaos block
`{type: kill-daemon, target: daemon_process, signal: SIGKILL, trigger:
step:fixer:running, operator: tt-chaos}` (US-003 schema; S29 calibration US-003 —
step:developer:running is not bfmw vocabulary, so the US-003 preflight rejects it): tt-chaos
resolves the CONTAINED daemon pid (never the production daemon) and SIGKILLs
it while the developer step is mid-round and the harness (pi) is still alive.

**Wired operator-seam action (S44a/S44b):** the manifest additionally
declares a single-run probe_sequence with the first-class
`restart_contained_daemon` probe op armed on `step:fixer:running` — the SAME
trigger as the chaos block — so the controller itself performs the restart
while the fixer step is in flight (the single-run daemon-lifecycle corridor;
`restart_daemon` remains the daemon-level MULTI-RUN op — the W3.22 shape).
The action restarts the CONTAINED daemon via `bin/daemon-control <kind>
restart` (kind `real` for the 43xx CLI / `scripted` for 53xx — the ONLY
sanctioned daemon-lifecycle path; never a bare `tamandua restart`, never the
operator's live 33xx daemon), records a per-action evidence record (op, argv,
exit code, provenance, path-invariant, observed effect), and fails closed
with the distinct category `restart-contained-daemon-failed` /
`daemon-path-invariant-violated` if the restart cannot be performed (S18c
stop-the-run — never a silent vacuous verdict). The recovery contract —
**late completion accepted; no requeue while
the group lives; recovery ≤ 2 dispatch intervals after the daemon exits** — is
judged from the run's event stream and terminal evidence (dispatch gap + run
completes) plus the restart action's observed effect; the typed
`restart_daemon` probe corridor with `recovery_within_dispatch_intervals` is
exercised by the companion row `W4.10-restart-recovery`.
