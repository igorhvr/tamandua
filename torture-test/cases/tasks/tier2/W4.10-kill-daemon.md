## Injection (typed chaos — kill-daemon) + operator restart seam

The manifest carries the typed chaos block
`{type: kill-daemon, target: daemon_process, signal: SIGKILL, trigger:
step:developer:running, operator: tt-chaos}` (US-003 schema): tt-chaos
resolves the CONTAINED daemon pid (never the production daemon) and SIGKILLs
it while the developer step is mid-round and the harness (pi) is still alive.

**Machinery delta (documented, not silent):** the `restart_daemon` probe op is
a daemon-level MULTI-RUN op by design (validateProbeSequence requires ≥ 2 run
groups — the W3.22 shape) and the validator rejects a chaos block alongside a
multi-run probe_sequence, so a single-run kill+restart corridor cannot carry a
typed `restart_daemon` probe action. Per the single-run daemon-lifecycle
pattern (W4.33a/W4.48a), the daemon restart here is an **OPERATOR action**
performed during the run: wait for the kill to land (~the fault phase), then
restart the contained daemon (contained env only — never the production
daemon). The recovery contract — **late completion accepted; no requeue while
the group lives; recovery ≤ 2 dispatch intervals after the daemon exits** — is
judged from the run's event stream and terminal evidence (dispatch gap + run
completes), not from a `restart_daemon` probe action. The typed
`restart_daemon` probe corridor with `recovery_within_dispatch_intervals` is
exercised by the companion row `W4.10-restart-recovery` (see
cases/tier2-traceability.md machinery deltas).
