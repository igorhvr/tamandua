# W4.32: ENOSPC — small loopback fs as TAMANDUA_WORKTREE_ROOT (resource exhaustion; gating)

Real pi run: bug-fix-merge-worktree (bfmw) on the **tt-ts** fixture
(`TEST_CMD` = `npm test`), with the run's worktrees rooted on a **small
loopback filesystem** so the bfmw overflows the fs mid-implement (spec 08 §C
W4.32 — the first resource-exhaustion coverage in the suite, DC48).

## Seeded defect (BUG-T1 — what the fixture actually contains)

The tt-ts seed `BUG-T1` (SEEDS.md catalog) implants an **A1 off-by-one** in
`src/store.ts` (`getByCategory` skips the last element). Dormant in the
baseline; the fixer writes the regression test.

## Loopback-fs setup (operator-choreographed, task-carried)

There is no probe/chaos op for mounting a filesystem; the setup is an
**OPERATOR action** performed before launch (documented machinery delta — see
cases/tier2-traceability.md):

1. Create a small loopback fs (e.g. `truncate -s <small> fs.img` +
   `mkfs` + `mount -o loop` — the bfmw is "sized to overflow mid-implement",
   so the fs must be large enough for checkout/install to begin but small
   enough that the implement-phase writes exhaust it). Use a CONTAINED mount
   point under `torture-test/var/` (e.g. `var/w4.32-lo`) — never a host path.
2. Point `TAMANDUA_WORKTREE_ROOT` at a directory ON that fs for the run's
   launch env (worktree-manager honors `TAMANDUA_WORKTREE_ROOT` verbatim).
3. Launch the bfmw; the run overflows the fs mid-implement.
4. After the run: unmount and remove the loop device (contained cleanup).

This deliberately violates the spec-01 "do not set TAMANDUA_WORKTREE_ROOT"
convention — the INJECTION is exactly that violation, and the case records
whether the failure is diagnosable with the DB intact.

## Expected (O10 unless noted)

- **Diagnosable failure:** the run fails with a diagnosable error naming the
  resource exhaustion (ENOSPC) — never a silent hang or a fabricated success.
- **DB intact:** the contained tamandua sqlite DB survives the overflow —
  no corruption, no lost ledger.
- **No phantom completion:** nothing lands as "completed" that did not; the
  run's terminal state is truthful (O1).
- **Worktree row consistent:** `run_worktrees`/worktree state reflects reality
  (no half-created worktree claimed as ready).
- The merged tree (if any partial landing occurred) is truthful (O2); the
  suite ledger stays consistent (O9).

## Caps note

Caps are sized for the SLOW loopback fs: wall 55 min = bfmw p50 35-min floor +
slow-fs margin (writes on the loopback fs are far slower than the host fs),
tokens at the pi bfmw family p95 (1M).
