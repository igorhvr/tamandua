# W4.03: Red-adjacent second commit — untested-tree landing bait (gating)

Real pi run: bug-fix-merge-worktree on tt-ts (seed `BUG-T3`). A chaos op lands
a **second commit on the bugfix branch AFTER the verifier attests**, so the
tree the merger would land (`MERGED_TREE`) differs from the attested
`TESTED_TREE` (red-adjacent evidence).

## Seeded defect (BUG-T3 — what the fixture actually contains)

The tt-ts fixture's seed `BUG-T3` (SEEDS.md catalog) implants an **A3 red-herring
ordering bug** in `src/store.ts`: `update()` splices the existing expense out
of its position and pushes the updated copy to the END of the internal array
instead of replacing in-place. The visible symptom (items reordering after an
edit in the UI) naturally suggests a frontend bug in `public/app.js`, but the
root cause is the store's `update()`. The regression test creates 3 expenses,
updates the middle one, and asserts `getAll()` preserves the original order.

## Injection (machinery delta — documented, not silent)

The spec's arming is a **post-verify second commit on the branch**: the tt-chaos
`colleague-commit` action (which makes a competing commit from a second-clone
perspective) lands a commit on the bugfix branch after the verifier computed
`TESTED_TREE` and before the merger's fast-forward check. The typed chaos block
currently exposes only `sigstop_sigcont | kill-harness | kill-daemon |
delete-tstx-row`; `colleague-commit` is implemented in bin/tt-chaos but not yet
exposed through the typed manifest block (see cases/tier2-traceability.md
machinery deltas). This case declares `chaos: null` and carries the injection
contract in this task text; wiring the block type is a follow-up execution
story. The injection must fire when the finalize step is pending
(`step:finalize_merge:pending` equivalent) so the extra commit exists when the
merger captures `EXPECT_TIP` and runs its FF check.

## Expected (O10 unless noted)

- **NEVER a green landing of an untested tree.** Either the attestation
  corridor catches the mismatch (`MERGED_TREE != TESTED_TREE` → fail-loud), or
  the rebase-loopback re-tests the moved branch. A silent green landing whose
  `MERGED_TREE` differs from the attested `TESTED_TREE` is the product finding.
- The oracle judges the merge gate evidence: `merge.landed` must carry a
  truthful annotation chain; a landing without re-verification of the moved
  tree is a violation.
