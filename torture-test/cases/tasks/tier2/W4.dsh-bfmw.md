## Seeded defect (BUG-T2 — what the fixture actually contains)

The tt-ts fixture's seed `BUG-T2` (SEEDS.md catalog) implants an **A2
two-module date-handling bug**: `src/server.ts` parses user-provided dates
from POST body with `new Date(dateStr).toISOString()`, producing full ISO
datetime strings with timezone offsets, while `src/store.ts` `getByDateRange`
uses naive string comparison (`localeCompare`). When a full ISO string like
`2025-06-15T15:00:00.000Z` is compared against a YYYY-MM-DD query, the `T`
sorts after end-of-string and the expense is excluded from exact-date
queries. Both files must be fixed (server normalizes to UTC midnight; store
compares UTC timestamps). The fixer's regression tests cover the
POST-normalization and date-range filtering paths. `TEST_CMD` is `npm test`
(FIXTURE.md).

## Injection (same drain barrier as W4.01)

1. `workflow pause --drain` fires while `verify` is still running
   (`step:verify:running`); the drain parks dispatch with `finalize_merge`
   promoted to pending.
2. `tt-chaos delete-tstx-row --tree <TESTED_TREE>` fires on
   `step:finalize_merge:pending` and deletes the tested tree's TSTX evidence

3. The daemon resumes and finalize dispatches with `missing` evidence under

The manifest's `chaos.tree` carries the sentinel `TESTEDTREE` — the execution
machinery resolves it to the run's attested `TESTED_TREE` before arming
tt-chaos.

## dsh-lane specifics (README dsh section)

- **DSH_PERMISSION_MODE injection:** the product injects
  `DSH_PERMISSION_MODE=danger-full-access` on every dsh worker spawn — the
  dsh equivalent of `--yolo`. Under dsh's default `workspace-write` sandbox,
  headless auto-DENIES (fail-closed, no prompt) any action outside the
  worktree — including `tamandua step complete`, which writes to
  `~/.tamandua` — so WITHOUT the injection the agent does the work but can
  never report it. The injection is process-scoped; nothing under `~/.dsh`
  is ever created or modified. The fixer/verifier/merger step reports must
  land: a step that wedges on an auto-denied `step complete` is a
  dsh-corridor finding (the refusal corridor itself is the product behavior
  under test, so a wedged step must be distinguished from the expected
  `refused_permanent`).
- **Profile-pin caveat:** dsh profile layers replace whole config rows, so an
  environment variable cannot beat them — if the profile's `cordis.patch.yml`
  (e.g. `~/.dsh/profiles/headless/cordis.patch.yml`) hard-pins
  sandbox/approval rows, the pin overrides the injection and out-of-worktree
  actions like `tamandua step complete` are auto-denied — breaking step
  reporting. The operator checks `tamandua doctor`'s permission-mode probe
  (warn-only) before judging a wedged step.
- **Token accounting:** dsh never prints token usage; the product reads the
  session log under `$DSH_HOME/sessions/<escaped-cwd>/session-<uuid>/
  session.jsonl.zstd` after each round (best-effort — unreadable store falls
  back to 0 tokens with a warning). An attribution gap (round ran but tokens
  read 0) is a finding to record, never a silent pass.
