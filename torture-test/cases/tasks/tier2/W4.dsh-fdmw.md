# W4.dsh-fdmw: colleague rebase on the moving target via dsh — rebase-loopback corridor (gating)

Real **dsh** run: feature-dev-merge-worktree (fdmw) on the **tt-go** fixture
(Go ≥ 1.21 worker-pool package, `TEST_CMD` = `go test ./...`, 33 green
baseline tests), launched through the dsh corridor (`--dsh-as-harness`).
This is the dsh-lane variant of spec 08 §B **W4.06**: the moving-target
rebase-loopback corridor is preserved, but the harness is dsh (alpha,
operator-directed) so the corridor also exercises the dsh-specific contracts
from the product README's dsh section. The feature to implement is the
fixture's **FEAT-G1** backlog item (FIXTURE.md "Seeded Features" catalog):
configurable pool size via the `TTGO_MAX_WORKERS` environment variable, with
invalid values silently falling back to the parameter, plus regression tests.

## What the fixture actually contains (FEAT-G1)

The tt-go fixture's FEAT-G1 feature is documented in `fixtures-src/tt-go/FIXTURE.md`
(Seeded Features table): `NewPool` must read `TTGO_MAX_WORKERS` and override
`maxWorkers` when it is a valid positive integer; unset/invalid values fall back
to the parameter. The acceptance boundaries are pinned there (env precedence,
invalid-value fallback, backward compatibility, test coverage for env
set/unset/invalid/zero). The fixture is Go-stdlib-only; `go test ./...` is the
canonical suite. There is NO seeded bug in the green baseline — the fdmw's job
is to implement the feature story-by-story and land it.

## Injection (machinery delta — documented, not silent)

Spec 08 §B W4.06: a colleague commits an **unrelated change to the target
branch** at ~T+15m and ~T+45m of the run's lifecycle, so the run's base
moves under it while the feature branch is still in flight. The injection is
tt-chaos `colleague-commit` (a competing commit from a second-clone
perspective) — implemented in bin/tt-chaos but **not** exposed in the typed
manifest chaos block (which offers only `sigstop_sigcont | kill-harness |
kill-daemon | delete-tstx-row`). This case carries `chaos: null` and the
injection contract lives here; wiring the block type is a follow-up execution
story (see cases/tier2-traceability.md machinery deltas). Per the wave-4
injection discipline, the commits are event-armed (never a bare sleep):
commit 1 fires when `step:developer:running` (≈ T+15m of a 138-min fdmw
lifecycle), commit 2 when `step:verify:running` (≈ T+45m). The commits must
touch files the feature work does NOT touch (e.g. `README.md`), so they are
unrelated to the run's diff.

## dsh-lane specifics (README dsh section)

- **DSH_PERMISSION_MODE injection:** the product injects
  `DSH_PERMISSION_MODE=danger-full-access` on every dsh worker spawn — the
  dsh equivalent of `--yolo`. Under dsh's default `workspace-write` sandbox,
  headless auto-DENIES (fail-closed, no prompt) any action outside the
  worktree — including `tamandua step complete`, which writes to
  `~/.tamandua` — so WITHOUT the injection the agent does the work but can
  never report it. The injection is process-scoped; nothing under `~/.dsh`
  is ever created or modified. Every step report (developer/planner/tester/
  merger) must land; a wedged step is a dsh-corridor finding, never a
  feature-work failure.
- **Profile-pin caveat:** dsh profile layers replace whole config rows, so an
  environment variable cannot beat them — if the profile's `cordis.patch.yml`
  (e.g. `~/.dsh/profiles/headless/cordis.patch.yml`) hard-pins
  sandbox/approval rows, the pin overrides the injection and out-of-worktree
  actions like `tamandua step complete` are auto-denied — breaking step
  reporting. The operator checks `tamandua doctor`'s permission-mode probe
  (warn-only) before judging a wedged step.
- **Token accounting:** dsh never prints token usage; the product reads the
  session log under `$DSH_HOME/sessions/<escaped-cwd>/session-<uuid>/
  session.jsonl.zstd` after each round (best-effort — unreadable store falls
  back to 0 tokens with a warning). An attribution gap (round ran but tokens
  read 0) is a finding to record, never a silent pass.

## Expected (O10 unless noted)

- **Rebase-loopback:** the merger's fast-forward/tip check detects the moved
  target and routes through the retry/`REBASED: true` corridor → the workflow
  re-runs `test` on the rebased branch → the tree is re-verified → the run
  lands. The landing must carry the truthful annotation chain (O2).
- **Reroute budget respected:** the rebase-loopback consumes reroutes from the
  fdmw finalize budget (`max_reroutes: 8`), never more than the corridor
  needs; a budget-exhaustion failure here is a product finding.
- **Zero false rugpulls:** base identity must come from the RECORDED refs
  (base-branch sha captured at launch), never from a live `HEAD` read of the
  moving target — a colleague's unrelated commit is a rebase event, NOT a
  rugpull; `run.rugpull_detected` firing for it is the finding.
- The dsh corridor must NOT change the rebase contract: `REBASED` semantics
  and reroute budget are harness-independent.

## Boundaries

- Work within the tt-go fixture (`pool.go`, `task.go`, `pool_test.go`, new
  tests). `TEST_CMD` is `go test ./...` — never `go test -race ./...` (the
  fixture's trap; BUG-G4 uses `-race`, FEAT-G1 does not).
- Do not modify `operator-notes.local`, `seeds/`, or `testdata/`.
- The colleague commits are the INJECTION, not part of the feature work.
