# W4.42: Shared-workdir refusal (scripted local-command cell, zero tokens)

Launch a SECOND run pointed at a workdir already owned by a LIVE run (same
working clone, both NON-WORKTREE / direct mode). The scenario cell
`scenarios/w4.42/shared-workdir-refusal/` launches two scripted DO-NOW rounds
(the do-now workflow is direct-mode — the bfmw workflow declares
`run.workspace: worktree` and REFUSES `--working-directory-for-harness`, a
documented machinery delta) at the same `--working-directory-for-harness`
clone; run-1 is launched first (no `--wait`, its doer behavior holds the
round open 30s), run-2 is fired once run-1 is admitted with a live dispatch
job.

## The pinned contract (spec 08 §J W4.42)

The daemon's admission gate (`src/server/control-server.ts` `admitOrQueueRun`)
refuses the second run with the OWNING run named (realpath-compared against
the daemon's in-memory job metadata; the `TAMANDUA_ALLOW_SHARED_HARNESS_WORKDIR`
escape hatch must NOT be set):

```
Run <run2> harness workdir is already scheduled for run <run1>: <workdir>
```

Asserted (mechanical, zero-token):

- run-1 completes cleanly (zero tokens);
- run-2 is REFUSED: its run row is `failed` and the refusal names the owning
  run (`run-1`'s id);
- NO interleaving: the shared clone stays at the baseline commit with a clean
  working tree (two agent teams interleaving commits in one index would be
  the S1).

## Expected

Deterministic refusal with the owning run named. Zero tokens. The cell is the
behaviors source + executable proof; the manifest row is a local-command cell
(`harness: local`, command hook `scenarios/lib/run-scripted-scenario`).

## Boundaries

- Scripted daemon only, contained ports; nothing outside `torture-test/var/`.


## Controller note (T2.1 US-009 — shared scripted-daemon bootstrap)

The operator-campaign PRODUCT_FAIL of this cell (exit 1 in ~1.3s with
`run-scripted-scenario: daemon-control scripted start failed` and a
`Terminated systemd-run ...` line) was a SHARED-BOOTSTRAP defect, not a
corridor defect: a concurrent campaign in worktree 862-c9ab2422 was starting
cells every few hundred ms, and each `daemon-control scripted start`
clean-slate (`systemctl --user stop tamandua-tt-scripted.scope`) SIGTERM'd
this worktree's just-created scope (journal: this campaign's scopes lived
146-533ms; the daemon never came up). Fixes (all in torture-test/, no
assertion weakened): bin/daemon-control now uses a PER-WORKTREE scope unit
name (`tamandua-tt-<kind>-<repo-root hash>`) so no other worktree can stop
or collide with this worktree's daemon; waits (bounded,
TT_DAEMON_PORT_WAIT_SECONDS, default 180s) for the kind's FIXED ports to
free before launching (concurrent worktrees serialize on the shared ports
instead of failing the bootstrap with EADDRINUSE); and clears a stale
tamandua.pid left by a killed daemon. This cell's run.sh additionally execs
its runner from the parent scenario dir (the runner lives beside the cell
dir). Full diagnosis: cases/tier2-traceability.md "Controller note (T2.1
US-009)".
