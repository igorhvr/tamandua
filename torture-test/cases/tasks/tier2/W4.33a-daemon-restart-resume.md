# W4.33a: Resume a paused run after daemon restart — leg (a) (gating)

Real pi run: bug-fix-merge-worktree (bfmw) on the **tt-ts** fixture
(`TEST_CMD` = `npm test`). Resume-composition leg (a) of spec 08 §G W4.33:
the run is paused, the contained daemon is restarted, and the run is
resumed — it must continue cleanly.

## Seeded defect (BUG-T3 — what the fixture actually contains)

The tt-ts seed `BUG-T3` (SEEDS.md catalog) implants an **A3 red-herring
ordering bug** in `src/store.ts`: `update()` splices the existing expense
out and pushes the updated copy to the END of the array instead of replacing
in-place, so `getAll()` reorders after any edit. The visible symptom suggests
a frontend bug in `public/app.js`, but the root cause is the store's
`update()`. The regression test creates 3 expenses, updates the middle one,
and asserts the original order is preserved.

## Injection / operator choreography

The probe sequence (manifest `probe_sequence`, single run group) expresses
the corridor the controller can automate:

1. `pause_drain` armed on `step:developer:running` with `hold_seconds: 600`
   (10-min hold). The drain lets the in-flight developer story finish, then
   parks dispatch with the run paused (`scheduling_status` draining).
2. **Operator action DURING the hold (this task's protocol):** restart the
   CONTAINED daemon out-of-band (the `restart_daemon` probe op is a
   multi-run-only capability by design — a single-run daemon restart is an
   operator seam; see cases/tier2-traceability.md machinery deltas). Use the
   contained env's daemon-control (`tamandua daemon restart` under the
   contained `TAMANDUA_STATE_DIR`), never the live daemon. The pause state is
   durably recorded in the contained DB, so the restarted daemon must re-read
   it and stay paused.
3. `resume` armed on `now` (fires as the hold ends): the run must continue
   from where it paused and complete.

## Expected (O10 unless noted)

- **Continues cleanly:** after the restart + resume, the run completes the
  full fix→verify→land cycle with a truthful annotation chain. A run that
  loses its pause state across the restart (next story dispatched during the
  hold / duplicate dispatch) or fails to resume is the product finding.
- **EXCLUSIVE WINDOW:** this is a daemon-lifecycle injection (spec 08
  preamble discipline 3). It takes a wave-lane exclusive window: no other W4
  scenario may be mid-arming on the contained daemon while its lifecycle is
  being violated. The controller must schedule this case alone on the
  contained instance (no concurrent case probing the same daemon).
- O16 judges the pause_drain effect (`drain_waits_current`,
  `next_story_parked`) and the resume's `run_completes` from the probe
  evidence; a dispatch event in the drain→resume window is
  `O16_DRAIN_DISPATCHED_NEXT_STORY`.
