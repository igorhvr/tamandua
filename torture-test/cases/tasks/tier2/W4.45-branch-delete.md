## Injection / operator choreography (no typed op)

There is no typed chaos/probe op for deleting a branch (the typed chaos block
exposes only sigstop_sigcont / kill-harness / kill-daemon / delete-tstx-row),
so the branch deletion is an **OPERATOR action** in the task text (machinery
delta, see `cases/tier2-traceability.md`):

1. Launch the bfmw run normally (worktree mode).
2. Wait until the fixer has created the feature branch and committed (armed on
   `step:verifier:running` — post-commit, PRE-finalize, so the deletion exists
   when the merger captures `EXPECT_TIP` and runs its FF check/landing).
3. Delete the feature branch in the worktree-ORIGIN repository:
   `git branch -D <feature-branch>` (resolved from the run context, verified
   under the contained `TAMANDUA_WORKTREE_ROOT` — target guards per the
   wave-4 injection discipline). The branch is the one the bfmw finalize step
   passes to `tamandua merge-branch --branch <branch> --expect-tip <sha>`.
4. Observe the landing: the merger's `--expect-tip` CAS or fetch must FAIL
   **LOUDLY with the missing-ref named** — never a silent re-create of the
   branch from a stale tip, never a landing of a resurrected wrong tree.

## Expected

- **The missing ref is named loudly.** The finalize step's merge-branch /
  fetch fails with a diagnosable error identifying the deleted branch (the
  branch or its tip is unresolvable); the run fails honestly with that
  diagnosis surfaced.
- **Never a silent re-create of the branch from a stale tip** (e.g. the
  merger recreating the branch at a cached/recorded sha and landing it).
- **Never a landing of a resurrected wrong tree:** no merge of a tree whose
  branch was deleted and re-materialized from stale metadata.
- The run terminates with a truthful terminal status + evidence naming the
  missing ref; the target ref is untouched by the deletion corridor.
- The seeded defect is the ONLY pre-existing defect.
