(`TEST_CMD` = `npm test`). Spec 08 §C W4.13: the run's managed worktree is

## Injection / operator choreography (no typed op)

There is no typed probe/chaos op for deleting a run worktree (the typed chaos
block exposes only sigstop_sigcont / kill-harness / kill-daemon /
delete-tstx-row), so the deletion is an **OPERATOR action** in the task text
(the W4.33c composition uses the same seam; this row is the standalone W4.13
corridor):

1. Launch the bfmw run normally (worktree mode).
2. Mid-run (armed on `step:developer:running`), delete the run's worktree
   OUT-OF-BAND: resolve the worktree path from the contained DB
   (`run_worktrees.worktree_path`), verify it is under the contained
   `TAMANDUA_WORKTREE_ROOT` (target guards per the wave-4 injection
   discipline), then `rm -rf` it.
3. Observe the run: the next dispatch diagnoses the missing worktree and the
   run fails with a diagnosable error naming the missing path — **never an
   infinite retry loop** against it.
4. Verify `run_worktrees` reflects reality (O6 backstop — not declared, see
   below): no phantom row claiming the deleted path is live; the row either
   records the removal/error truthfully or the run's terminal evidence names
   the missing worktree.
