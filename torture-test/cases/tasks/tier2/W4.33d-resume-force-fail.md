# W4.33d-resume-force-fail: Resume after a CLI force-fail — directly-constructed state (S49 split — constructed-state arm)

Scripted-pi run (zero tokens): bug-fix-merge-worktree (bfmw) on the **tt-ts**
fixture (`TEST_CMD` = `npm test`, seed `BUG-T4`), executed by the scripted-pi
runtime on the contained scripted daemon. This is the **directly-constructed-
state** cell of the S49 W4.33d split (see `cases/tier2-traceability.md` §S49).

## Premise the cell pins

Spec 08 §G W4.33 leg (d) — the documented **"fix the underlying issue then
`workflow resume`"** path (AGENTS.md): a run that has permanently failed
restarts from its failed step with context intact and completes. The former
real `W4.33d-reroute-exhaustion-resume` cell tried to reach the failed state
by exhausting `max_reroutes` with a persistent chaos target move — a premise
that never fired in three real-campaign redesigns (S29 typed chaos, S36
per-attempt re-arm, mac campaign #1): the product absorbs the moves and the
run never permanently fails.

**This cell exercises the resume VECTOR without relying on that race: it
CONSTRUCTS the failed state directly with the CLI force-fail
(`workflow fail <run-id> --reason ... --force`, the probe engine's
`fail_force` op).** No chaos, no timing — the failure is deterministic.

## Seeded defect (BUG-T4 — what the fixture actually contains)

The tt-ts seed `BUG-T4` (SEEDS.md catalog) implants an **A4 performance
defect** in `src/store.ts`: `getByCategory` becomes O(n²) (nested loops +
`JSON.stringify` comparisons, ~4M calls for 2,000 expenses). Dormant in the
baseline; the regression test creates 2,000 expenses and asserts completion
under 50ms.

## Injection / deterministic choreography (no race)

The manifest probe sequence (single run group):

1. **`fail_force` armed on `step:finalize_merge:running`** — fires as the
   finalize step's worker is in flight: the contained CLI runs
   `workflow fail <run-id> --reason 'torture-test probe fail_force' --force`,
   which cancels the non-done steps and sets the run to terminal `failed`
   (emitting `run.force_failed`). Constructed by the CLI — never dependent on
   chaos cadence or reroute budgets.
2. **`resume` armed on `event:run.force_failed`** (the constructed failure's
   own event) with `expect.run_completes: true` — fires once the run is
   durably `failed`: `workflow resume <run-id>` resets the interrupted
   pipeline from the first non-done step (the force-failed shape: canceled
   steps return to `waiting`), re-registers with the contained daemon, and
   the SAME run id re-dispatches and completes.

The scripted merger is a plain `done` behavior (a single honest landing) —
the failure that the resume repairs comes from the CLI force-fail, never from
a scripted retry storm.

## Expected (pinned, mechanical)

- **The failure is constructed, not raced:** `run.force_failed` fires, the run
  reaches terminal `failed`, and the resume probe fires on it (probe evidence
  records both actions with exit codes; S45 daemon-reported semantics apply
  to the resume).
- **Resume picks up from the failed step with context intact:** the resumed
  run restarts from the interrupted finalize (not from the top), the original
  context (task, test_cmd, seed) is unchanged, and the SAME run id completes
  to a truthful single landing (`run.completed`) — O16 `run_completes` PASS.
- A resume that restarts the whole pipeline, drops context, or double-applies
  work is the finding.
- Zero tokens (scripted-pi runtime + system tripwire).
