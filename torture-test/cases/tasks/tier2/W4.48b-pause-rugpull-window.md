# W4.48b: Composed fault — pause during the rugpull window (characterization)

Real pi run: bug-fix-merge-worktree (bfmw) on the **tt-ts** fixture
(`TEST_CMD` = `npm test`). Composed-fault arm (b) of spec 08 §G W4.48:
`workflow pause` is issued between target-moved detection and the relaunch

## Seeded defect (BUG-T2 — what the fixture actually contains)

The tt-ts seed `BUG-T2` (SEEDS.md catalog) implants an **A2 two-module
date-handling bug** (`src/server.ts` ISO-normalizes POST dates,
`src/store.ts` compares them naively → exact-date queries miss day-boundary
expenses). Dormant in the baseline; fix spans both files.

## Injection / probe choreography

The target-moved detection comes from the same injection as W4.08 (a
colleague commit moves the target during finalize — tt-chaos
`move-branch`/`colleague-commit`, untyped → `chaos: null` + machinery delta
in cases/tier2-traceability.md). The probe sequence (manifest
`probe_sequence`, single run group):

1. `pause` armed on `event:merge.target_moved` with `hold_seconds: 600`
   (10-min hold). `merge.target_moved` is a real product event emitted by the
   merger when its expected-tip check fails — the pause lands between
   detection and the rugpull decision. (Arming note: the run is still
   `running` at that instant — the CLI refuses to pause a non-running run; if
   the poll observes the event only after the run transitioned to failed, the
   pause is refused and the corridor must be re-armed. The refusal itself is
   evidence, recorded by the probe.)
2. `resume` armed on `now` (fires as the hold ends) — the relaunch machinery
   resumes (or the paused state suppresses it).

No `expect` is declared: the corridor is one-of-two, so O16's hardcoded
resume-completes judgment is deliberately NOT attached to this case (its
oracle set omits O16; the probe evidence is recorded and the corridor is
judged from this task's contract + O1's terminal-state read).

## Composition prerequisites

- **Single-fault ancestors green first:** the rugpull corridor's single-fault
  ancestor is W4.08 (no-relaunch + control) — both must be green before this
  composed fault is interpretable.
- This arm is NOT a daemon-lifecycle injection (it is a control-plane pause),
  but it interleaves with the relaunch machinery, so it still requires an
  exclusive scheduling window on the contained instance (no concurrent W4
  scenario mid-arming on the same daemon while the pause/relaunch interplay is
  observed).

## Expected (characterization — pinned observation)

- **Exactly one of {relaunch, paused-no-relaunch}:** after the pause is
  lifted, the rugpull corridor must produce EXACTLY ONE terminal outcome —
  either the replacement run relaunches (and completes/behaves per O1), or no
  relaunch occurs (the run stays failed with the suppression/diagnosis
  surfaced).
- **Never a relaunch that starts paused-orphaned:** the replacement run must
  not start in a paused-orphaned state (registered, then never dispatched,
  with no resume path).
- **Never double relaunch on resume:** the pause+resume cycle must not cause
  TWO replacement runs. Zero or two replacements is the finding.
- The observed branch (relaunch vs paused-no-relaunch) is recorded in the
  attempt evidence with the event trail (`run.rugpull_detected`,
  `run.rugpull_relaunched` / suppression) — the characterization output.
