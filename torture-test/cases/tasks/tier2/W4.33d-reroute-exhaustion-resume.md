# W4.33d: Reroute-exhaustion resume — the documented `workflow resume` path, leg (d) (gating)

Real pi run: bug-fix-merge-worktree (bfmw) on the **tt-ts** fixture
(`TEST_CMD` = `npm test`). Resume-composition leg (d) of spec 08 §G W4.33:
a persistent consumer-rejection condition exhausts `max_reroutes` → the run
permanently fails; the condition is removed; `workflow resume` picks up from
the failed step with context intact and the run completes — the documented
"fix the underlying issue then resume" path (AGENTS.md), tested nowhere else.

## Seeded defect (BUG-T4 — what the fixture actually contains)

The tt-ts seed `BUG-T4` (SEEDS.md catalog) implants an **A4 performance
defect** in `src/store.ts`: `getByCategory` becomes O(n²) (nested loops +
`JSON.stringify` comparisons, ~4M calls for 2,000 expenses). Dormant in the
baseline (small test datasets); the regression test creates 2,000 expenses
and asserts completion under 50ms.

## Injection / operator choreography

The persistent consumer-rejection condition is a **persistent target move**:
the bfmw finalize step (`on_fail.retry_step: verify`, `max_reroutes: 8`,
`retry_on: [target_moved, conflicts]`) keeps failing because a colleague
keeps committing to the target branch — each reroute re-runs verify, then the
finalize hits a moved target again, until the reroute budget exhausts and the
run permanently fails (terminal `run.failed`).

- **The colleague target-move is a TYPED `move-branch` chaos block (US-004
  premise redesign).** The manifest `chaos` block declares
  `type: move-branch, target: origin_target_ref, trigger:
  step:finalize_merge:running, ref: refs/heads/seed/BUG-T4, repeat: 60,
  interval_s: 60, wait_timeout_s: 4200, rearm: true, rearm_hold_s: 3`. The
  controller resolves the origin repository (the provisioned work clone
  handed to `--worktree-origin-repository`), verifies
  `refs/heads/seed/BUG-T4` resolves there (the seeded branch the bfmw merger merges into for this cell's BUG-T4 seed — NOT main),
  and spawns `bin/tt-chaos move-branch` under the contained spawn env —
  **the injection is genuinely executed** (previously `chaos: null`, so no
  colleague commit ever moved the target and `event:run.failed` never fired:
  the S29 premise-redesign defect).
- **Persistent pressure, bounded + self-standing-down.** tt-chaos first arms
  an empty-diff "colleague budget" of commits on the target ref (so the
  single-commit tt-ts main has parents to walk back through — the target's
  TREE never changes, so downstream merges stay clean).
- **Per-attempt deterministic re-arm (US-007 S36 redesign).** The move loop
  is NOT a free-running clock (the S36 root cause: at `interval_s 60` a
  free-running cadence landed a move inside a finalize attempt's expected-tip
  window only when the window happened to straddle the next tick — exactly
  ONE move did, the run rerouted once and completed cleanly, and
  `event:run.failed` never fired). With `rearm: true` each FRESH
  `step:finalize_merge:running` occurrence — the step transitions
  waiting→pending→running on every reroute cycle — triggers the NEXT move
  after the `rearm_hold_s: 3` post-marker hold (so the merger's tip capture
  precedes the move; `interval_s` becomes a minimum-spacing floor, never a
  cadence). Every finalize attempt therefore observes a moved tip →
  `merge-branch --expect-tip` sees the moved tip → `merge.target_moved` →
  `STATUS: retry` → reroute to verify → the next attempt re-arms the next
  move → ... until attempt 9 exhausts `max_reroutes: 8`
  (`step.reroute_budget_exhausted`) and the run permanently fails
  (`event:run.failed` FIRES). The loop STANDS DOWN as soon as the run is
  observed terminal (run status OR a run.* terminal event in the append-only
  event stream) — the "operator removes the rejection condition" protocol is
  mechanized: the colleague commits stop at `run.failed`, so the resumed
  finalize runs against a stable target.
- **Probe (manifest `probe_sequence`, single run group):** `resume` armed on
  `event:run.failed` with `expect.run_completes: true`. The probe fires the
  contained `workflow resume <run-id>` when the run permanently fails.
- **Operator action before the resume fires (this task's protocol):** with
  the typed chaos block this is AUTOMATED — the chaos loop's run-terminal
  stand-down IS the removal of the rejection condition, so the resumed
  finalize runs against a stable target. (The `repeat` budget is the
  operator's stand-down authority: the moves stop at budget end or at
  run-terminal, whichever comes first.)

## Expected (O10 unless noted)

- **Reroute exhaustion is honest:** the run permanently fails ONLY after the
  `max_reroutes` budget is consumed (the terminal `run.failed` names the
  reroute exhaustion), never wedged mid-cycle and never silently retried
  past the budget.
- **Resume picks up from the failed step with context intact:** the resumed
  run restarts from the failed `finalize_merge` step (not from the top), the
  original context (task, test_cmd, seed) is unchanged, and the run completes
  to a truthful landing with the correct annotation chain. O16 judges the
  resume's `run_completes` (same run id completes).
- A resume that restarts the whole pipeline, drops context, or double-applies
  work is the finding.
