# W4.23: Daemon stop under node runtime A, start under runtime B, same DB — zero behavioral drift (DC44) (scripted, zero tokens; gating)

Scripted local-command case (zero tokens): the scenario cell
`scenarios/w4.23/daemon-cross-runtime-restart/` stops the contained scripted
daemon under node runtime A and starts it under node runtime B against the
SAME DB (spec 08 §H W4.23 — "Daemon stop under runtime A, start under
runtime B, same DB. Zero behavioral drift (DC44)").

## Host-adaptation predicate (documented choice)

- `requires.capabilities = ["node-sqlite", "node-runtimes-2"]`: the
  `node-runtimes-2` capability is RECORDED by W0.0 (tt-verify-environment)
  as a Boolean leaf under `host-profile.json` `capabilities.node-runtimes-2`
  — true iff the host has ≥ 2 DISTINCT node runtimes/versions (discovered
  from volta image dirs + nvm version dirs, deduped by version, each with a
  sqlite probe; US-011 extends the node-version check). A host with fewer
  than 2 distinct runtimes gates `NOT_RUN (predicate)` with evidence — the
  corridor is untestable there. The EXACT key is `capabilities.node-runtimes-2`
  (E2.2 canonical contract; documented in case.schema.json + oracles/CONTRACT.md).
- `requires.platform = "linux"` + `containment ["systemd-user-scope"]`:
  the daemon-lifecycle restart runs through the contained daemon-control
  (the tier0/lifecycle cell platform).
- The standard cell shape: `capabilities ["node-sqlite"]`, `node_min 22`.

## What the scenario actually exercises (per spec)

The runner resolves the host's node runtimes (the same discovery
tt-verify-environment uses), picks runtime A (the current/default node) and
runtime B (a SECOND distinct node binary that loads `node:sqlite` — probed;
fails closed with a diagnosable message if no secondary sqlite-capable
runtime exists), then:

- **Under runtime A:** the contained scripted daemon is up (harness-started).
  A scripted do-now run completes; the DB state (runs/steps rows for that
  run) and the `sqlite_master` schema are captured.
- **Stop under A:** `daemon-control scripted stop` (with the scenario's
  `TAMANDUA_SCRIPTED_BEHAVIORS`/`TAMANDUA_SCRIPTED_STATE` forwarded).
- **Start under B (T2.2 US-004 — post-S24/US-006 mechanism):** daemon-control
  reconstructs the contained launch PATH itself (`contained_path_for_kind` —
  var/adapters-bin first, env-script PATH next, caller PATH last), so a
  caller-PATH prepend of runtime B's bin dir is DROPPED. The scenario
  therefore switches the daemon through daemon-control's sanctioned
  `TT_DC_ENV_SCRIPTED` env-script seam: it writes a CONTAINED env-script
  variant under torture-test/var (generated by
  `scenarios/lib/runtime-switch-env.mjs`, shared with the regression
  self-test) that sources `env/tt-env-scripted.sh` and pins
  `TT_NODE_BIN`/`TT_NODE_BIN_DIR` + PATH to runtime B, and runs
  `daemon-control scripted start/status/stop` with
  `TT_DC_ENV_SCRIPTED=<variant>` for the runtime-B phase ONLY — the
  launcher's `exec node` then resolves from the variant's PATH and the daemon
  lands on runtime B's binary (asserted via the daemon PID's resolved node
  executable). The SAME `TAMANDUA_STATE_DIR` DB is opened (same path — the DB
  is shared, never copied).
- **Zero behavioral drift (DC44):** (1) the schema (`sqlite_master`) is
  byte-identical; (2) runtime-A's run rows (runs/steps/stories) survive the
  restart byte-identically; (3) `daemon status` + the control plane respond
  identically under B; (4) a SECOND scripted do-now completes under B with
  the same step sequence/behavior as under A — zero drift across the runtime
  switch.
