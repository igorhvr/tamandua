# W4.dsh-lifecycle: resume a paused dsh run after daemon restart — leg (a) (gating)

Real **dsh** run: bug-fix-merge-worktree (bfmw) on the **tt-ts** fixture
(`TEST_CMD` = `npm test`), launched through the dsh corridor
(`--dsh-as-harness`). This is the dsh-lane variant of spec 08 §G **W4.33
leg (a)** (resume composition): the run is paused, the contained daemon is
restarted, and the run is resumed — it must continue cleanly — but the
harness is dsh (alpha, operator-directed) so the corridor also exercises the
dsh-specific contracts from the product README's dsh section.

## Seeded defect (BUG-T3 — what the fixture actually contains)

The tt-ts seed `BUG-T3` (SEEDS.md catalog) implants an **A3 red-herring
ordering bug** in `src/store.ts`: `update()` splices the existing expense
out and pushes the updated copy to the END of the array instead of replacing
in-place, so `getAll()` reorders after any edit. The visible symptom suggests
a frontend bug in `public/app.js`, but the root cause is the store's
`update()`. The regression test creates 3 expenses, updates the middle one,
and asserts the original order is preserved. `TEST_CMD` is `npm test`
(FIXTURE.md).

## Injection / operator choreography

The probe sequence (manifest `probe_sequence`, single run group) expresses
the corridor the controller can automate:

1. `pause_drain` armed on `step:fixer:running` with `hold_seconds: 600`
   (10-min hold; S29 calibration US-003 — the bfmw coding step; the old
   `step:developer:running` is not bfmw vocabulary, so the US-003 preflight
   rejects it). The drain lets the in-flight fixer story finish, then
   parks dispatch with the run paused (`scheduling_status` draining).
2. **Operator action DURING the hold (this task's protocol):** restart the
   CONTAINED daemon out-of-band (the `restart_daemon` probe op is a
   multi-run-only capability by design — a single-run daemon restart is an
   operator seam; see cases/tier2-traceability.md machinery deltas). Use the
   contained env's daemon-control (`tamandua daemon restart` under the
   contained `TAMANDUA_STATE_DIR`), never the live daemon. The pause state is
   durably recorded in the contained DB, so the restarted daemon must re-read
   it and stay paused.
3. `resume` armed on `now` (fires as the hold ends): the run must continue
   from where it paused and complete.

## dsh-lane specifics (README dsh section)

- **DSH_PERMISSION_MODE injection:** the product injects
  `DSH_PERMISSION_MODE=danger-full-access` on every dsh worker spawn — the
  dsh equivalent of `--yolo`. Under dsh's default `workspace-write` sandbox,
  headless auto-DENIES (fail-closed, no prompt) any action outside the
  worktree — including `tamandua step complete`, which writes to
  `~/.tamandua` — so WITHOUT the injection the agent does the work but can
  never report it. The injection is process-scoped; nothing under `~/.dsh`
  is ever created or modified. Every step report must land across the
  daemon restart; a step that wedges after the restart on an auto-denied
  report is a dsh-corridor finding, never a pause-state failure.
- **Profile-pin caveat:** dsh profile layers replace whole config rows, so an
  environment variable cannot beat them — if the profile's `cordis.patch.yml`
  (e.g. `~/.dsh/profiles/headless/cordis.patch.yml`) hard-pins
  sandbox/approval rows, the pin overrides the injection and out-of-worktree
  actions like `tamandua step complete` are auto-denied — breaking step
  reporting. The operator checks `tamandua doctor`'s permission-mode probe
  (warn-only) before judging a wedged step.
- **Token accounting:** dsh never prints token usage; the product reads the
  session log under `$DSH_HOME/sessions/<escaped-cwd>/session-<uuid>/
  session.jsonl.zstd` after each round (best-effort — unreadable store falls
  back to 0 tokens with a warning). A pause/restart/resume cycle that loses
  token attribution across the daemon restart is a finding to record, never a
  silent pass.

## Expected (O10 unless noted)

- **Continues cleanly:** after the restart + resume, the run completes the
  full fix→verify→land cycle with a truthful annotation chain. A run that
  loses its pause state across the restart (next story dispatched during the
  hold / duplicate dispatch) or fails to resume is the product finding.
- **EXCLUSIVE WINDOW:** this is a daemon-lifecycle injection (spec 08
  preamble discipline 3). It takes a wave-lane exclusive window: no other W4
  scenario may be mid-arming on the contained daemon while its lifecycle is
  being violated. The controller must schedule this case alone on the
  contained instance (no concurrent case probing the same daemon).
- O16 judges the pause_drain effect (`drain_waits_current`,
  `next_story_parked`) and the resume's `run_completes` from the probe
  evidence; a dispatch event in the drain→resume window is
  `O16_DRAIN_DISPATCHED_NEXT_STORY`.
