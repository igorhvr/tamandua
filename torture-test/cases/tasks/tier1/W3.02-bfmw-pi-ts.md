### BUG SYMPTOM (A2 — two-module coordinated bug)

Date-based filtering returns inconsistent results: expenses near day boundaries are missing from query results. **Both modules must be fixed** — a single-file fix leaves the symptom in place.

1. **POST dates are stored as full ISO datetime strings with timezone offsets.** In `src/server.ts`, a user-provided `date` from the POST body is parsed with `new Date(dateStr).toISOString()`, which produces a full ISO datetime string with a timezone offset (e.g. `2025-06-15T15:00:00.000Z` for `2025-06-15` in UTC-3).

2. **`getByDateRange()` filters with naive string comparison.** In `src/store.ts`, date-range filtering compares date strings with `localeCompare`. A full ISO string like `2025-06-15T15:00:00.000Z` compared against a YYYY-MM-DD query like `"2025-06-15"` sorts after it (the `T` character sorts after end-of-string), so the expense is excluded from exact-date queries.

Reproduction: POST an expense with `date: "2025-06-15"`, then GET `/api/expenses?startDate=2025-06-15&endDate=2025-06-15` — the expense is not found.

**This is a two-module bug (archetype A2):** the two defects are coordinated — fixing only one module leaves the symptom. In `src/server.ts`, normalize dates to UTC midnight YYYY-MM-DD (e.g. `new Date(cleanDate + 'T00:00:00Z').toISOString().split('T')[0]`). In `src/store.ts`, replace the string comparison with UTC timestamp comparison (`new Date(date).getTime()`). Investigate both modules and fix both; do not stop after the first fix works.
