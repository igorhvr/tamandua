### BUG SYMPTOM (red-herring archetype)

After editing an expense in the UI, the edited item moves to the end of the expense list. The displayed totals are still computed correctly from the full list — only the ordering is corrupted.

The natural place to look is the frontend rendering in `public/app.js` — items reordering/jumping after an edit suggests a DOM manipulation bug. But the actual root cause is `update()` in `src/store.ts`: it splices the existing expense out of its position and pushes the updated copy to the end of the internal array, instead of replacing it in place. As a result, `getAll()` returns expenses in a different order after any `update()` call.

**This is a red-herring:** the symptom points at `app.js`, but the defect is in `store.ts`. You must investigate past the obvious target. Fix `update()` to replace in place (`this.#expenses[index] = updated` — no splice, no push), and add a regression test for order preservation: create 3 expenses, update the middle one, and assert `getAll()` preserves the original order `[e1, e2-updated, e3]`. Name the regression test with the `BUG-T3` tag (e.g. `preserves expense order in getAll() after update (regression BUG-T3)`). Hermes' longer round and retry chain makes the investigation depth requirement realistic.
